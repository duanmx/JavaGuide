# Java 并发编程 - 操作系统前置知识

> 并发编程的本质是在多核 CPU 上让多个线程安全地共享内存。不理解底层发生了什么，就无法理解为什么需要 volatile、synchronized、CAS 这些机制。

---

## 一、进程与线程

### 1.1 进程（Process）

进程是操作系统**资源分配**的最小单位。

```
┌─────────────────────────────────────┐
│           进程（Process）             │
│                                     │
│  独立的资源：                         │
│  ├── 虚拟地址空间（代码段、数据段、堆） │
│  ├── 文件描述符表                     │
│  ├── 信号处理配置                     │
│  └── 进程控制块（PCB）                │
│                                     │
│  包含 1 个或多个线程                   │
└─────────────────────────────────────┘
```

**核心特征**：
- 进程之间**内存隔离**，A 进程不能直接读写 B 进程的内存
- 进程间通信（IPC）需要通过操作系统提供的机制：管道、消息队列、共享内存、Socket 等
- 创建和销毁进程的**开销大**（需要分配/回收整套资源）

### 1.2 线程（Thread）

线程是操作系统**CPU 调度**的最小单位。

```
┌──────────────────────────────────────────────────┐
│                   进程（JVM 进程）                  │
│                                                  │
│  共享资源（所有线程可见）：                          │
│  ├── 堆内存（Heap）            ← 对象实例           │
│  ├── 方法区（Metaspace）       ← 类元信息           │
│  └── 进程级文件描述符                               │
│                                                  │
│  线程私有（每个线程独立一份）：                       │
│  ├── 程序计数器（PC）           ← 当前执行到哪条指令  │
│  ├── 寄存器                    ← CPU 正在处理的数据  │
│  ├── 虚拟机栈（VM Stack）       ← 方法调用栈帧       │
│  ├── 本地方法栈（Native Stack） ← C/C++ 调用栈帧    │
│  └── 线程本地存储（TLS / ThreadLocal）              │
└──────────────────────────────────────────────────┘
```

**核心特征**：
- 同一进程内的线程**共享堆内存**，这是并发问题的根源
- 线程切换比进程切换**轻量得多**（只需保存/恢复寄存器和栈，不需要切换地址空间）
- 每个线程有自己的**程序计数器 + 寄存器 + 栈**，切换时需要保存上下文

### 1.3 线程 vs 进程对比

| 维度 | 进程 | 线程 |
|------|------|------|
| 调度单位 | 资源分配单位 | CPU 调度单位 |
| 内存 | 独立地址空间，互不可见 | **共享堆内存**（并发问题根源） |
| 切换开销 | 大（需要切换页表、刷新 TLB） | 小（只保存寄存器 + 栈） |
| 创建/销毁 | 重（fork + exec） | 轻（分配栈空间即可） |
| 通信方式 | 需要 IPC 机制 | **直接读写共享变量**（需要同步） |
| 崩溃影响 | 一个进程崩溃不影响其他进程 | 一个线程崩溃可能**导致整个进程崩溃** |

### 1.4 Java 线程与操作系统线程的关系

**HotSpot JVM 采用 1:1 线程模型**：每个 Java 线程直接对应一个操作系统原生线程（Native Thread）。

```
Java 线程                        操作系统线程
┌──────────┐                   ┌──────────────┐
│ Thread A │ ←──── 1:1 ──────▶│ OS Thread A  │
├──────────┤                   ├──────────────┤
│ Thread B │ ←──── 1:1 ──────▶│ OS Thread B  │
├──────────┤                   ├──────────────┤
│ Thread C │ ←──── 1:1 ──────▶│ OS Thread C  │
└──────────┘                   └──────────────┘
```

**这意味着**：
- Java 线程的创建、调度、切换**全部由操作系统内核完成**
- 线程阻塞（如 `synchronized` 获取锁失败）会让线程进入**内核态**，代价较高
- JVM 无法绕过操作系统去优化线程调度

> **面试话术**：HotSpot 使用 1:1 线程模型，Java 线程直接映射到操作系统原生线程，线程调度和切换由内核完成。好处是实现简单、能充分利用多核；缺点是线程创建和切换开销较大，这也是为什么需要线程池的原因。

## 二、线程上下文切换

### 2.1 切换流程

当 CPU 从线程 A 切换到线程 B 时：

```
① 保存线程 A 的上下文
   程序计数器（PC） → 存到 A 的内核栈
   寄存器值        → 存到 A 的内核栈

② 加载线程 B 的上下文
   从 B 的内核栈恢复 PC
   从 B 的内核栈恢复寄存器

③ 跳转到 B 的 PC 位置继续执行
```

### 2.2 切换开销

| 开销来源 | 说明 |
|---------|------|
| 保存/恢复寄存器 | 直接开销，通常几十纳秒 |
| 缓存失效（冷缓存） | **最大开销**：切换后新线程的数据不在 L1/L2 缓存中 |
| TLB 刷新 | 地址转换缓存失效，内存访问变慢 |
| 内核态切换 | 用户态 → 内核态 → 用户态，两次上下文切换 |

> **面试话术**：线程切换最大的隐性开销不是保存寄存器，而是**缓存失效**。切换后新线程需要重新从主存加载数据到 L1/L2 缓存，这段时间内 CPU 性能大幅下降。这也是为什么线程数不是越多越好的根本原因。

### 2.3 对并发编程的启示

- **线程数 ≠ 性能**：线程太多 → 频繁切换 → 缓存反复失效 → 性能反而下降
- **减少切换**：批量处理、减少锁竞争、使用无锁数据结构，都是为了减少上下文切换
- **CPU 密集型线程数 ≈ CPU 核心数**：避免无谓的切换

## 三、CPU 缓存体系

### 3.1 为什么需要缓存？

CPU 和主存之间存在巨大的**速度鸿沟**：

```
组件              访问延迟
─────────────────────────────
CPU 寄存器         ~0.5 ns
L1 缓存（32-64KB） ~1 ns      ← 和 CPU 同频
L2 缓存（256KB-1MB）~4 ns
L3 缓存（数MB-数十MB）~10-20 ns ← 所有核心共享
主存（DRAM）        ~100 ns    ← 比 L1 慢 100 倍
磁盘               ~10 ms     ← 比主存慢 10 万倍
网络               ~100 ms
```

> 缓存存在的唯一理由：**CPU 太快了，主存跟不上。**

### 3.2 多级缓存架构

```
        ┌──────┐  ┌──────┐  ┌──────┐  ┌──────┐
        │Core 0│  │Core 1│  │Core 2│  │Core 3│
        └──┬───┘  └──┬───┘  └──┬───┘  └──┬───┘
           │         │         │         │
        ┌──┴───┐  ┌──┴───┐  ┌──┴───┐  ┌──┴───┐
        │ L1   │  │ L1   │  │ L1   │  │ L1   │  每个核心私有
        │ D + I│  │ D + I│  │ D + I│  │ D + I│  （数据缓存 + 指令缓存）
        └──┬───┘  └──┬───┘  └──┬───┘  └──┬───┘
           │         │         │         │
        ┌──┴───┐  ┌──┴───┐  ┌──┴───┐  ┌──┴───┐
        │  L2  │  │  L2  │  │  L2  │  │  L2  │  每个核心私有
        └──┬───┘  └──┬───┘  └──┬───┘  └──┬───┘
           │         │         │         │
           └─────────┴────┬────┴─────────┘
                          │
                   ┌──────┴──────┐
                   │     L3      │  所有核心共享（Last Level Cache）
                   └──────┬──────┘
                          │
                   ┌──────┴──────┐
                   │   主存 DRAM  │
                   └─────────────┘
```

**核心要点**：
- **L1/L2 是核心私有的**：Core 0 的 L1/L2 和 Core 1 的 L1/L2 是**物理隔离的**
- **L3 是所有核心共享的**：又称 LLC（Last Level Cache）
- 数据从主存 → L3 → L2 → L1 → 寄存器，逐级向上搬运

### 3.3 缓存行（Cache Line）

缓存不是按字节读取的，而是按**缓存行（Cache Line）**为单位批量读取。

```
缓存行大小：通常 64 字节（x86 架构）

主存地址：0x1000
    ↓ 按 64 字节对齐
一次加载 0x1000 ~ 0x103F（64 字节）到缓存行
```

**对并发编程的影响 —— 伪共享（False Sharing）**：

```
问题场景：两个线程分别操作不同变量，但这两个变量恰好在同一个缓存行中

┌─── 缓存行（64 字节）───────────┐
│ ... │ 变量 A │ ... │ 变量 B │ ... │
└──────────────────────────────────┘
  ↑                   ↑
线程 1 频繁修改 A     线程 2 频繁修改 B

结果：线程 1 修改 A → 整个缓存行失效 → 线程 2 的 L1/L2 中 B 也失效了
     → 线程 2 被迫重新从主存加载 → 性能暴跌
```

**解决方案**：

```java
// 方案 1：@Contended 注解（JDK 1.8+），在字段前后填充 128 字节隔离
@sun.misc.Contended
private volatile long value;

// 方案 2：手动填充（JDK 1.8 之前的做法）
class PaddedAtomicLong {
    long p1, p2, p3, p4, p5, p6;  // 填充 48 字节
    volatile long value;            // 8 字节
    long p7, p8, p9, p10, p11, p12; // 填充 48 字节
}
```

> **面试话术**：伪共享是多线程性能杀手。两个线程操作不同变量，但因为变量在同一个 64 字节缓存行中，一个线程的写操作会导致另一个线程的缓存行失效，频繁从主存加载，性能严重下降。JDK 1.8 引入 `@Contended` 注解通过在字段前后填充字节来隔离缓存行。

## 四、缓存一致性问题

### 4.1 问题的根源

多核 CPU 的 L1/L2 缓存是**核心私有的**，当多个核心同时读写同一个变量时：

```
时间线：
                    Core 0 的 L1          Core 1 的 L1
                    ┌──────────┐          ┌──────────┐
                    │ x = 10   │          │ x = 10   │  （各自缓存了一份 x）
                    └──────────┘          └──────────┘

Core 0 执行 x = 20：
                    ┌──────────┐          ┌──────────┐
                    │ x = 20 ✅│          │ x = 10 ❌│  Core 1 还是旧值！
                    └──────────┘          └──────────┘

→ 这就是"可见性问题"的硬件根源
→ Java 的 volatile 就是为了解决这个问题
```

### 4.2 MESI 协议（缓存一致性协议）

现代 CPU 通过**缓存一致性协议**保证多个核心的缓存数据一致。最经典的是 **MESI 协议**。

每个缓存行有 4 种状态：

| 状态 | 英文 | 含义 |
|------|------|------|
| **M** | Modified（已修改） | 本核心独占修改过，和主存不一致，**脏数据** |
| **E** | Exclusive（独占） | 本核心独占，和主存一致，只有我有这份缓存 |
| **S** | Shared（共享） | 多个核心都有这份缓存，和主存一致，**只读** |
| **I** | Invalid（无效） | 这份缓存已过期，不可使用 |

### 4.3 MESI 状态转换（以 x 为例）

```
初始：x = 10 在主存中，没有核心缓存

① Core 0 读取 x
   Core 0 L1: x = 10 [E]（独占，只有我有）

② Core 1 也读取 x
   Core 0 L1: x = 10 [S]（变成共享）
   Core 1 L1: x = 10 [S]（共享）

③ Core 0 写入 x = 20
   Core 0 L1: x = 20 [M]（已修改，脏数据）
   Core 1 L1: x = 10 [I]（被通知失效！）← 通过总线嗅探

④ Core 1 再读取 x
   发现自己是 [I] 状态 → 向 Core 0 请求最新数据
   Core 0 将 x = 20 写回主存（或直接从缓存转发）
   Core 0 L1: x = 20 [S]
   Core 1 L1: x = 20 [S]（拿到最新值）
```

### 4.4 MESI 协议的关键机制

**总线嗅探（Bus Snooping）**：
- 每个核心都在"监听"总线上的事务
- Core 0 要写 x 时，在总线上发出"我要修改 x"的信号
- Core 1 嗅探到这个信号，发现自己的缓存行有 x → 主动将自己标记为 [I]（无效）

**写回（Write Back）策略**：
- M 状态的数据不会立刻写回主存，而是在**被其他核心请求时**或**被替换出缓存时**才写回
- 这比"写穿（Write Through）"策略性能好得多（减少总线流量）

## 4.5 MESI 没有锁，怎么保证一致性？

MESI 协议本身**不使用软件锁**，而是通过**硬件级别的原子操作**保证一致性。

### 机制一：总线串行化（硬件隐式锁）

多个核心同时想写同一个变量时，谁先谁后？—— **总线仲裁**。

```
Core 0 要写 x = 20
Core 1 也要写 x = 30

┌─────────────────────────────────────────────────┐
│              共享总线 / 互连网络                   │
│                                                 │
│  Core 0 ──▶ 发出 BusRdX 信号（我要独占 x）        │
│  Core 1 ──▶ 发出 BusRdX 信号（我要独占 x）        │
│                                                 │
│  总线仲裁器：同一时刻只允许一个核心的请求通过         │
│  → Core 0 先获得总线 → Core 1 等待                │
└─────────────────────────────────────────────────┘
```

总线本身就是串行的：同一时刻只有一个核心能发出写请求，相当于硬件层面隐式的"全局互斥"。

### 机制二：写入前的失效确认（Invalidate + ACK 握手）

这是 MESI 保证一致性的**关键机制**：

```
Core 0 要写 x = 20，完整流程：

① Core 0 在总线上发出 Invalidate 请求
   "我要修改地址 x，你们有 x 的缓存行全部作废"

② Core 1 收到请求，发现自己的 L1 中有 x
   → 将 x 的缓存行标记为 [I]（无效）
   → 给 Core 0 回一个 ACK（确认已失效）

③ Core 0 必须等到所有持有 x 缓存的核心都回复 ACK
   → 全部收到 ACK 后，才真正执行 x = 20

④ Core 0 的缓存行状态变为 [M]（独占修改）
```

```
时间线：

Core 0                          总线                     Core 1
  │                              │                         │
  │── Invalidate(x) ────────────▶│──── 广播 ──────────────▶│
  │                              │                         │
  │                              │          发现缓存中有 x   │
  │                              │          标记为 [I]       │
  │                              │                         │
  │◀───── ACK ──────────────────│◀──── ACK（我已失效）─────│
  │                              │                         │
  │ 所有 ACK 到齐                 │                         │
  │ → 执行 x = 20               │                         │
  │ → 状态 [M]                   │                         │
```

> **关键点**：这是硬件强制的握手协议——写操作必须等所有 ACK 返回后才真正执行，不可能出现"写了但别人不知道"的情况。

### 机制三：缓存间传输（Cache-to-Cache Transfer）

B 后续怎么读到最新值？

```
Core 1 执行 int v = x;

① 检查 L1 缓存 → 发现 x 的状态是 [I]（无效）
② 不能直接用 → 在总线上发出 Read 请求
③ Core 0 嗅探到 Read 请求，发现自己是 [M] 状态
   → 把最新数据（x=20）通过缓存间传输发给 Core 1
   → 同时将自己从 [M] 降为 [S]
④ Core 1 拿到 x=20，状态为 [S]
⑤ Core 1 读到 v = 20 ✅
```

### 三层保障总结

| 机制 | 作用 | 类比 |
|------|------|------|
| **总线串行化** | 同一时刻只有一个核心能写 | 相当于隐式的"全局锁" |
| **Invalidate + ACK 握手** | 写之前确保其他核心缓存已失效 | 相当于"写前通知所有人清除旧数据" |
| **Cache-to-Cache Transfer** | M 状态的缓存直接转发给读请求 | 保证读方能拿到最新值 |

> **面试话术**：MESI 协议不使用软件锁，而是通过硬件级别的原子操作保证一致性。总线仲裁保证同一时刻只有一个核心能发起写操作（相当于硬件隐式锁），Invalidate + ACK 握手机制保证写入前所有其他核心的缓存都已失效，Cache-to-Cache Transfer 保证读方能从 M 状态的核心拿到最新数据。三者配合，使得多核缓存在没有软件干预的情况下也能保持一致。Java 的 `volatile` 就是在这个硬件机制之上加了**内存屏障**（Memory Barrier），确保编译器和 CPU 不会对 volatile 操作进行重排序，从而在软件层面完整实现了 JMM 的可见性和有序性保证。

### 4.6 从 MESI 到 Java volatile 的映射

```
Java 代码                              MESI 协议行为
─────────────────────────────────────────────────────
volatile int x = 10;                   
                                       所有核心缓存行标记为 [I]
Core 0: x = 20;（写 volatile）
                                       Core 0 的缓存行 → [M]
                                       其他核心的缓存行 → [I]（总线通知）
                                       强制写回主存

Core 1: int v = x;（读 volatile）
                                       Core 1 发现 [I] → 从主存/其他核心加载最新值
                                       保证读到 20
```

> **核心结论**：
> - `volatile` 写 → 触发 MESI 的失效通知，保证其他核心缓存行失效
> - `volatile` 读 → 强制从主存/最新缓存加载，保证可见性
> - Java 内存模型（JMM）是对 MESI 等硬件协议的**软件层面抽象**

## 五、管程（Monitor）

> 管程是操作系统理论中解决并发同步问题的经典模型。Java 的 `synchronized` 关键字底层就是基于管程实现的。理解管程，是打通「操作系统理论 → JVM 实现 → Java 并发编程」的关键一环。

### 5.1 管程是什么？

管程（Monitor，音译：**冒尼特**）是一种**同步机制**，它将共享数据和对数据的操作封装在一起，保证**同一时刻最多只有一个线程能执行管程内的代码**。

```
管程的核心思想：
┌─────────────────────────────────────┐
│           管程（Monitor）              │
│                                     │
│  共享数据（只有管程内部能访问）          │
│  + 对数据的操作（互斥执行）            │
│  + 条件变量（线程间的协调等待）         │
│                                     │
│  规则：同一时刻只有一个线程能进入        │
└─────────────────────────────────────┘
```

**管程解决了三个问题**：

| 问题 | 管程的解决方案 |
|------|---------------|
| 互斥（Mutual Exclusion） | 同一时刻只允许一个线程进入 |
| 同步（Synchronization） | 通过条件变量实现线程间等待/唤醒 |
| 封装（Encapsulation） | 共享数据对外不可见，只能通过管程操作 |

### 5.2 管程的理论模型

管程有两种经典实现流派：

| 模型 | 代表 | wait 后的行为 | 谁继续执行？ |
|------|------|-------------|-------------|
| **Hoare 管程** | 理论模型 | 立即唤醒等待线程，新唤醒的线程**优先执行** | 被唤醒的线程 |
| **MESA 管程** | 工程实现（Java/C/Pthread） | 唤醒等待线程，但**当前线程继续执行**直到退出管程 | 当前线程 |

**Java 采用的是 MESA 模型**（也叫 Mesa 管程）。

```
MESA 模型的执行流程：

线程 A（持有管程）              线程 B（在条件变量上等待）
    │                              │
    │ 执行 notify()               │
    │ → B 被放入入口队列            │
    │                              │
    │ 继续执行（A 还没退出管程）     │
    │ ...                          │
    │                              │
    │ 退出管程（释放锁）            │
    │                              │
    │                          B 竞争管程成功
    │                          B 从 wait() 返回
    │                          B 继续执行
```

> **关键细节**：MESA 模型中，`notify()` 唤醒的线程**不会立即执行**，而是要等当前线程退出管程（释放锁）后，才有机会竞争锁。这就是为什么 Java 中 `notify()` 后，被唤醒的线程还需要重新获取锁才能从 `wait()` 返回。

### 5.3 Java 对象与管程的关系

**每个 Java 对象天生自带一个管程（Monitor）**，这就是 JVM 的设计：

```
Java 对象内存布局：
┌────────────────────────────────────┐
│          Java 对象                   │
│                                    │
│  ┌────────────────────────────┐    │
│  │ 对象头（Object Header）      │    │
│  │  ├── Mark Word（锁信息）     │    │
│  │  └── Klass Pointer ──────────┼──▶ 指向元空间中的类元信息
│  └────────────────────────────┘    │
│                                    │
│  实例数据（Instance Data）           │
│  对齐填充（Padding）                │
└────────────────────────────────────┘
         │
         │ 膨胀后关联
         ▼
┌────────────────────────────────────┐
│     ObjectMonitor（重量级锁）        │
│                                    │
│  _owner: 当前持有锁的线程            │
│  _count: 重入计数                    │
│                                    │
│  _EntryList: 阻塞等待获取锁的线程队列 │
│  _WaitSet:   调用了 wait() 的线程队列 │
└────────────────────────────────────┘
```

**什么时候创建 ObjectMonitor？**

不是每个对象一创建就有 ObjectMonitor，只有在锁膨胀到**重量级锁**时才创建：

```
synchronized 加锁流程：

① 偏向锁：Mark Word 记录偏向线程 ID（无 ObjectMonitor）
   ↓ 出现第二个线程竞争
② 轻量级锁：栈帧中创建 Lock Record，CAS 尝试获取（无 ObjectMonitor）
   ↓ 竞争激烈，CAS 失败
③ 重量级锁：创建 ObjectMonitor，关联到 Mark Word
   → 竞争失败的线程进入 _EntryList 阻塞
```

### 5.4 ObjectMonitor 的内部结构详解

```
┌──────────────────────────────────────────────────────┐
│                   ObjectMonitor                       │
│                                                      │
│  ┌────────────────────────────────────────────────┐  │

│  │ _count: int         重入次数（同一线程多次加锁）  │  │
│  │ _recursions: int    递归重入计数                  │  │
│  └────────────────────────────────────────────────┘  │
│                                                      │
│  ┌────────────────────────────────────────────────┐  │
│  │          _EntryList（入口等待队列）                │  │
│  │                                                │  │
│  │  线程竞争锁失败 → 进入 _EntryList → 被 park 挂起  │  │
│  │                                                │  │
│  │  ┌────────┐  ┌────────┐  ┌────────┐            │  │
│  │  │Thread B│→│Thread C│→│Thread D│→ NULL       │  │
│  │  │(park)  │  │(park)  │  │(park)  │            │  │
│  │  └────────┘  └────────┘  └────────┘            │  │
│  └────────────────────────────────────────────────┘  │
│                                                      │

│  │                                                │  │

│  │                                                │  │
│  │  ┌────────┐  ┌────────┐                        │  │
│  │  │Thread E│→│Thread F│→ NULL                   │  │

│  │  └────────┘  └────────┘                        │  │
│  └────────────────────────────────────────────────┘  │
└──────────────────────────────────────────────────────┘
```

### 5.5 synchronized 与 monitor 的完整交互流程

#### 加锁流程

```
线程 A 执行 synchronized(obj) {

① 字节码层面：monitorenter 指令

② JVM 检查 Mark Word 的锁状态：

   [偏向锁] → 检查偏向线程 ID 是否是 A
     → 是：直接进入，无开销
     → 否：撤销偏向，升级为轻量级锁

   [轻量级锁] → CAS 将 Mark Word 替换为指向 Lock Record 的指针
     → 成功：获得锁，继续执行
     → 失败：自旋重试几次
       → 仍然失败：升级为重量级锁

   [重量级锁] → 尝试获取 ObjectMonitor
     → _owner == null：A 成为 _owner，_count = 1，进入临界区
     → _owner == A（重入）：_count + 1，继续执行
     → _owner == B（被其他线程持有）：
       → A 被封装为 ObjectWaiter 节点
       → 放入 _EntryList
       → park(A) 挂起线程 A
       → A 进入 BLOCKED 状态
```

#### 解锁流程

```
线程 A 执行 } // synchronized 块结束

① 字节码层面：monitorexit 指令

② _count - 1

③ _count > 0：重入未完全释放，返回

④ _count == 0：完全释放
   → _owner = null
   → 从 _EntryList 中取出一个线程（通常是等待最久的）
   → unpark(该线程)
   → 该线程被唤醒，重新竞争 monitor
```

#### wait / notify 与 monitor 的交互

```
线程 A 持有 monitor，执行 obj.wait()：

① 检查 A 是否是 monitor 的 _owner
   → 不是：抛出 IllegalMonitorStateException

② _count 暂存，_owner = null（释放 monitor）

③ A 被封装为 ObjectWaiter 节点
   → 放入 _WaitSet
   → park(A) 挂起
   → A 进入 WAITING 状态

线程 B 持有 monitor，执行 obj.notify()：

① 检查 B 是否是 monitor 的 _owner
   → 不是：抛出 IllegalMonitorStateException

② 从 _WaitSet 中取出一个节点（通常是最早等待的）
   → 将该节点移到 _EntryList
   → 注意：此时 A 没有立即被唤醒！

③ B 继续执行，直到退出 synchronized 块
   → B 释放 monitor
   → 从 _EntryList 取出 A → unpark(A)
   → A 竞争 monitor 成功后，从 wait() 返回
```

### 5.6 monitor 重入机制

synchronized 是可重入锁，靠 `_count` 实现：

```java
synchronized (obj) {           // monitorenter: _owner=A, _count=1
    synchronized (obj) {       // monitorenter: _owner=A, _count=2（重入）
        synchronized (obj) {   // monitorenter: _owner=A, _count=3（重入）
            // ...
        }                      // monitorexit:  _count=2
    }                          // monitorexit:  _count=1
}                              // monitorexit:  _count=0, _owner=null, 真正释放
```

```
重入计数流程：

monitorenter #1  →  _count = 1
monitorenter #2  →  _count = 2（同一线程，直接 +1）
monitorenter #3  →  _count = 3
monitorexit  #1  →  _count = 2
monitorexit  #2  →  _count = 1
monitorexit  #3  →  _count = 0 → 释放锁，唤醒 _EntryList 中的等待线程
```

> 如果没有重入机制，同一个线程在嵌套 synchronized 块中会**自己把自己锁住（死锁）**。

### 5.7 轻量级锁如何避免创建 monitor？

JDK 6 优化的核心思想：**大部分 synchronized 块执行时根本没有竞争**，不需要创建重量级的 ObjectMonitor。

```
轻量级锁的工作流程：

① 线程 A 进入 synchronized 块
   → 在 A 的栈帧中创建 Lock Record（锁记录）
   → CAS 将对象的 Mark Word 复制到 Lock Record 中
   → CAS 成功：将 Mark Word 替换为指向 Lock Record 的指针
   → 获得轻量级锁，继续执行

② 线程 B 也进入 synchronized 块
   → 在 B 的栈帧中创建 Lock Record
   → CAS 尝试替换 Mark Word → 失败（已被 A 占用）
   → B 开始自旋（循环重试 CAS）

③ B 自旋若干次后仍然失败
   → 锁膨胀为重量级锁
   → 创建 ObjectMonitor
   → B 进入 _EntryList，被 park 挂起

栈帧中的 Lock Record：
┌─────────────────┐
│  栈帧            │
│  ├── 局部变量    │
│  ├── Lock Record │  ← 轻量级锁的核心数据结构
│  │   ├── Displaced Mark Word（备份原始 Mark Word）
│  │   └── owner → 指向被锁对象
│  └── ...         │
└─────────────────┘
```

> **面试话术**：synchronized 的锁升级过程本质上是管程的"轻量化实现"。无竞争时，用栈帧中的 Lock Record 代替 ObjectMonitor，避免内核态切换；有竞争时，才创建完整的 ObjectMonitor 进入内核态阻塞。整个设计思路是**按需分配同步资源**。

### 5.8 管程 vs 其他同步原语

| 原语 | 机制 | 互斥 | 条件等待 | Java 对应 |
|------|------|------|---------|----------|
| **互斥锁（Mutex）** | 加锁/解锁 | ✅ | ❌ | `ReentrantLock`（简化版） |
| **信号量（Semaphore）** | P/V 操作（计数器） | ✅（计数=1 时） | ❌ | `java.util.concurrent.Semaphore` |
| **管程（Monitor）** | 互斥 + 条件变量 | ✅ | ✅ | `synchronized` + `wait/notify` |
| **条件变量（Condition）** | 配合互斥锁使用 | 需配合锁 | ✅ | `Lock.newCondition()` |

```
管程 = 互斥锁 + 条件变量

synchronized  = monitor 的互斥部分
wait/notify   = monitor 的条件变量部分

ReentrantLock + Condition = 更灵活的管程
  → 可以创建多个条件变量（管程只有一个 _WaitSet）
  → 可以中断等待、可以超时
```

### 5.9 从管程视角看常见面试题

**Q：synchronized 和 ReentrantLock 的本质区别是什么？**

```
从管程的角度看：

synchronized：
  → 直接使用 JVM 内置的 ObjectMonitor（系统管程）
  → 一个 monitor 只有一个 _WaitSet（条件等待队列）
  → notify() 只能随机唤醒一个线程
  → 由 JVM 管理，无需手动释放

ReentrantLock + Condition：
  → 用户层面的管程实现（基于 AQS）
  → 可以创建多个 Condition（多个条件等待队列）
  → signal() 可以精确唤醒特定条件上的线程
  → 需要手动 lock/unlock
```

```java
// synchronized 只有一个 waitSet
synchronized (obj) {
    obj.wait();      // 所有等待的线程都在同一个队列
    obj.notify();    // 随机唤醒一个，无法区分等待条件
}

// ReentrantLock 可以有多个 Condition
ReentrantLock lock = new ReentrantLock();
Condition notFull  = lock.newCondition();  // 队列不满条件
Condition notEmpty = lock.newCondition();  // 队列不空条件

lock.lock();
notEmpty.await();     // 在"不空"条件上等待
notEmpty.signal();    // 精确唤醒等待"不空"的线程
notFull.signal();     // 精确唤醒等待"不满"的线程
lock.unlock();
```

## 六、用户态与内核态

### 6.1 两种执行模式

```
┌─────────────────────────────────────┐
│             用户态（User Mode）       │
│  ┌───────────────────────────────┐  │
│  │  Java 应用代码                 │  │
│  │  ├── 普通计算                  │  │
│  │  ├── 对象创建                  │  │
│  │  └── 非阻塞操作                │  │
│  └───────────────────────────────┘  │
│              ↓ 系统调用               │
├─────────────────────────────────────┤
│             内核态（Kernel Mode）     │
│  ┌───────────────────────────────┐  │
│  │  操作系统内核                   │  │
│  │  ├── 线程调度                  │  │
│  │  ├── 锁的阻塞/唤醒（mutex）    │  │
│  │  ├── 内存分配（mmap）          │  │
│  │  └── 网络 I/O                  │  │
│  └───────────────────────────────┘  │
└─────────────────────────────────────┘
```

### 6.2 哪些操作会进入内核态？

| 操作 | 进内核态的原因 |
|------|--------------|
| `synchronized` 获取锁失败（重量级锁） | 需要内核 mutex 阻塞线程 |
| `Thread.sleep()` | 需要内核定时器 |
| `LockSupport.park()` | 需要内核阻塞线程 |
| 线程创建/销毁 | 需要内核分配/回收线程资源 |
| 线程上下文切换 | 由内核调度器完成 |
| 文件 I/O | 需要内核访问文件系统 |

### 6.3 对并发编程的启示

**减少用户态 → 内核态切换是高性能并发的关键**：

```
性能排序（从高到低）：

① 无锁操作（纯用户态）           → 最快
   volatile 读写、CAS
   ↑ 不需要进内核

② 轻量级锁（用户态自旋）          → 较快
   synchronized 低竞争时
   ↑ 在用户态 CAS 尝试获取锁

③ 重量级锁（进内核阻塞）          → 最慢
   synchronized 高竞争时
   ↑ 需要内核 mutex，涉及上下文切换
```

> **面试话术**：JDK 6 的锁升级机制本质上就是尽可能在用户态解决问题。偏向锁和轻量级锁完全在用户态完成，只有竞争激烈时才膨胀为重量级锁进入内核态阻塞。这是因为用户态到内核态的切换本身就有微秒级的开销。

## 七、线程挂起的内核机制（Mutex vs futex）

> synchronized 和 ReentrantLock 获取锁失败时都会把线程挂起，但它们在操作系统内核里走的是**完全不同的路径**。理解这个区别，是真正理解 Java 并发底层原理的最后一步。

### 7.1 synchronized 的内核路径：OS Mutex

synchronized 重量级锁在 Linux 上使用操作系统的 **pthread_mutex** 实现。

```
synchronized 获取锁失败
    ↓
JVM 调用 pthread_mutex_lock()
    ↓
═══════════════════════════════════════
          进入内核（系统调用）
═══════════════════════════════════════

内核维护的 mutex 结构：
┌─────────────────────────────────────────────────────┐
│  struct mutex {                                     │
│      atomic_t count;        ← 锁计数（0=已锁定）      │
│      spinlock_t wait_lock;  ← 保护等待队列的自旋锁    │
│      list_head wait_list;   ← 等待队列（内核维护！）   │
│  }                                                  │
│                                                     │
│  pthread_mutex_lock() 失败时：                       │
│  ① 把当前线程加入 wait_list（内核操作）                │
│  ② 调度器把线程从运行队列移除                          │
│  ③ 切换到下一个线程执行                               │
│                                                     │
│  pthread_mutex_unlock() 时：                         │
│  ① 从 wait_list 取出一个线程（内核自动决定！）          │
│  ② 把该线程放回运行队列                               │
│  ③ 调度器择机调度该线程                                │
└─────────────────────────────────────────────────────┘
```

**关键特征**：等待队列由**内核维护**，唤醒哪个线程由**内核决定**，JVM 完全交出控制权。

### 7.2 LockSupport.park() 的内核路径：futex

LockSupport.park() 在 Linux 上使用 **futex**（Fast Userspace muTEX，音译：**菲尤泰克斯**）实现。

```
LockSupport.park()
    ↓
Unsafe.park()
    ↓
JVM 调用 futex(addr, FUTEX_WAIT, 0, NULL)
    ↓
═══════════════════════════════════════
          进入内核（系统调用）
═══════════════════════════════════════

futex 的内核本质：一张“床位登记表”
┌─────────────────────────────────────┐
│      futex 内核等待表                 │
│                                     │
│  地址 0x7F001234 → [线程A, 线程C]    │
│  地址 0x7F005678 → [线程B]           │
│  地址 0x7F009ABC → []               │
│                                     │
└─────────────────────────────────────┘

内核只做两件事，没有任何复杂逻辑：

FUTEX_WAIT（挂起）：
  ① 读取用户态地址的值，检查是否 == 期望值
     → 不等于：状态已变，不需要挂起，直接返回
     → 等于：继续
  ② 把当前线程登记到该地址的等待队列
  ③ 把线程从 CPU 运行队列移除
  ④ 线程状态设为 TASK_INTERRUPTIBLE
  ⑤ 调用 schedule()，让出 CPU

FUTEX_WAKE（唤醒）：
  ① 查找该地址的等待队列
  ② 取出 N 个线程（N 由参数指定）
  ③ 把这些线程放回 CPU 运行队列
```

**关键特征**：内核**不管“谁在等、等什么”**，只负责“这个地址上挂着的线程，叫醒 N 个”。排队逻辑完全由 JVM 在用户态通过 AQS 的 CLH 队列自主管理。

### 7.3 两者的内核差异对比

```
OS Mutex（synchronized）                 futex（LockSupport）
────────────────────                    ────────────────────

内核数据结构：                           内核数据结构：
┌─────────────────────┐                ┌─────────────────────────┐
│ struct mutex {      │                │ futex 全局哈希表          │
│   wait_list: [A,B]  │                │  地址X → [A]             │
│   owner: thread_X   │                │  地址Y → [B,C]           │
│   count: 0          │                │  （就这些，没有 owner）   │
│ }                   │                │ }                        │
└─────────────────────┘                └─────────────────────────┘

内核知道：                               内核知道：
“这把锁是谁持有的，谁在等它”                “这个地址上有线程在睡觉”
→ 内核知道完整的锁语义                    → 内核不知道任何语义
→ 解锁时内核自动选线程唤醒                → 必须由 JVM 告诉内核“唤醒谁”

JVM 的角色：                             JVM 的角色：
旁观者（把线程交给内核，由内核管理）        管理者（自己管理排队逻辑，
                                        只让内核做“睡/醒”动作）
```

| 维度 | OS Mutex（synchronized） | futex（LockSupport） |
|------|-------------------------|--------------------------|
| 内核数据结构 | `struct mutex`（带完整等待队列） | 一个用户态整数 + 内核等待队列 |
| 谁维护等待队列 | **内核全权管理**（自动入队出队） | **JVM 自己管理**（AQS CLH 队列） |
| 唤醒逻辑 | unlock 时内核**自动**选线程唤醒 | 内核不自动唤醒，必须由 JVM **显式**调 FUTEX_WAKE |
| 语义绑定 | 绑定到具体锁（知道 owner 是谁） | 不绑定任何语义（只知道地址上有线程在等） |
| 灵活性 | 低（内核固定逻辑） | 高（JVM 可自定义排队策略） |

### 7.4 futex 为什么叫 “Fast”？

```
传统 pthread_mutex：
  加锁 → 系统调用 → 进入内核 → 检查锁状态 → 可能阻塞
  解锁 → 系统调用 → 进入内核 → 检查等待队列 → 可能唤醒

  即使没有竞争，每次加锁/解锁也要进内核！
  用户态 → 内核态切换 ≈ 几百纳秒 ~ 1 微秒

futex：
  无竞争时：纯用户态原子操作（CAS），不进内核
           延迟 ≈ 几纳秒
  有竞争时：才走系统调用进内核挂起

性能对比（无竞争加锁/解锁 1 亿次）：
  pthread_mutex：~3 秒（每次都进内核）
  futex：         ~0.3 秒（全在用户态完成）
  → 快 10 倍！
```

> “Fast” 的本质：**无竞争时完全不需要进入内核**，把最热的路径留在用户态。

### 7.5 对应到 Java 锁升级的本质

```
偏向锁：     纯用户态（Mark Word 记录线程 ID）
             ≈ 比 futex 还快（连 CAS 都不需要）

轻量级锁：   用户态 CAS（Lock Record），不进内核
             ≈ futex 无竞争时的快速路径

重量级锁：   OS Mutex，进内核阻塞
             ≈ 传统 pthread_mutex

ReentrantLock：AQS + LockSupport.park → futex
             无竞争：用户态 CAS（state 0→1），不进内核
             有竞争：futex_wait 进内核挂起
             → 相当于“智能版”的 futex，JVM 自己控制排队逻辑
```

### 7.6 permit 许可机制（LockSupport 独有）

LockSupport 在 JVM 层面还有一个 **permit（许可）** 机制，这是 futex 本身不具备的、由 JVM 额外提供的功能：

```
park()：
  permit == 1 → 消耗 permit（permit=0），不挂起，直接返回
  permit == 0 → 挂起线程

unpark()：
  permit 设为 1
  如果线程正在 park → 唤醒线程
```

**permit 的特殊性**：

```java
// unpark 可以先于 park 调用！
LockSupport.unpark(thread);  // permit = 1（线程还没 park）
thread.start();

// 线程启动后执行 park()
// permit == 1 → 消耗 permit → 不挂起！直接继续执行
```

```java
// 但 permit 不累积
LockSupport.unpark(thread);  // permit = 1
LockSupport.unpark(thread);  // permit 还是 1（不是 2）

thread.park();  // 消耗 permit，不挂起
thread.park();  // permit=0，挂起！
```

> **面试话术**：synchronized 重量级锁和 LockSupport.park 在操作系统层面走的是完全不同的路径。synchronized 使用 OS 的 mutex 原语，等待队列由内核维护，唤醒逻辑由内核自动完成，JVM 失去控制权。LockSupport.park 使用 Linux 的 futex 原语（Fast Userspace Mutex），内核只负责最基本的挂起/唤醒，等待队列和唤醒策略完全由 JVM 在用户态通过 AQS 的 CLH 队列自主管理。futex 的“Fast”体现在无竞争时完全不需要进入内核，这也是 ReentrantLock 在高并发场景下比 synchronized 重量级锁更灵活的根本原因——JVM 可以在用户态实现更精细的排队和唤醒策略，包括 permit 许可机制（unpark 可以先于 park 调用，避免唤醒丢失）。

## 总结：操作系统知识如何映射到 Java 并发

| 操作系统概念 | Java 并发对应机制 | 解决的什么问题 |
|-------------|-----------------|--------------|
| 线程共享堆内存 | 并发访问同一变量 | 为什么需要同步 |
| 上下文切换开销 | 线程池、减少锁竞争 | 为什么线程不是越多越好 |
| L1/L2 缓存私有 | 可见性问题 | 为什么需要 volatile |
| 缓存行 64 字节 | 伪共享 | 为什么 AtomicInteger 数组要做填充 |
| MESI 缓存一致性 | volatile 的语义 | 硬件层面如何保证可见性 |
| 管程（Monitor） | synchronized + wait/notify | 互斥与条件等待的封装 |
| OS Mutex vs futex | synchronized vs ReentrantLock | 内核全托管 vs JVM 自主管理 |
| 用户态/内核态切换 | 锁升级机制 | 为什么 synchronized 有锁升级 |

> 理解了这些底层机制，Java 并发编程中的所有设计（volatile、synchronized、CAS、AQS、线程池）都不再是需要死记硬背的知识点，而是**为了解决具体硬件问题而自然产生的方案**。
