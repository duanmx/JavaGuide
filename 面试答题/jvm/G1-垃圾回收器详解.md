# G1 垃圾回收器详解

---

## 一、核心设计思想

**G1（Garbage First）** 的名字含义是"优先回收垃圾最多的区域"。它打破了传统分代收集器把堆物理划分为固定新生代/老年代的模式，改为将堆划分为大量等大的 **Region**，通过逻辑方式实现分代。

```
传统收集器（CMS/Parallel）：
┌──────────────────────┬──────────────────────┐
│      新生代（固定）    │      老年代（固定）    │
│  Eden + S0 + S1      │                      │
└──────────────────────┴──────────────────────┘

G1：
┌───┬───┬───┬───┬───┬───┬───┬───┬───┬───┐
│ E │ E │ S │ O │ O │ H │ E │ O │ E │ O │
└───┴───┴───┴───┴───┴───┴───┴───┴───┴───┘
  E=Eden  S=Survivor  O=Old  H=Humongous
  每个 Region 可以动态扮演不同角色
```

---

## 二、Region 模型

```
堆被划分为约 2048 个等大 Region
Region 大小：1MB ~ 32MB（必须是 2 的幂）
  -XX:G1HeapRegionSize 可手动指定
  默认自动计算：堆大小 / 2048

例如：
  堆 = 8GB  → Region = 4MB
  堆 = 32GB → Region = 16MB
  堆 = 64GB → Region = 32MB
```

**四种 Region 类型**：

| Region 类型 | 作用 |
|------------|------|
| **Eden Region** | 存放新创建的对象 |
| **Survivor Region** | 存放 Young GC 存活对象 |
| **Old Region** | 存放长期存活对象 |
| **Humongous Region** | 存放大对象（> Region 大小的 50%） |

## 三、G1 的三种 GC 过程

### 1. Young GC（新生代回收）

```
触发条件：所有 Eden Region 都被填满

回收范围：所有 Eden Region + 所有 Survivor Region
算法：复制算法（Mark-Copy）

过程：
  ① STW（Stop The World），暂停所有应用线程
  ② 从 GC Roots 出发，标记新生代 Region 中的存活对象
  ③ 将存活对象复制到新的 Survivor Region（或晋升到 Old Region）
  ④ 清空原来的 Eden 和 Survivor Region
  ⑤ 恢复应用线程

特点：
  - 只回收新生代，不碰老年代
  - 停顿时间较短（通常 20~100ms）
```

### 2. Mixed GC（混合回收）— G1 的核心创新

```
触发条件：老年代占用达到 IHOP 阈值
  -XX:InitiatingHeapOccupancyPercent（默认 45%）

回收范围：所有新生代 Region + 部分老年代 Region
算法：新生代用复制算法，老年代用标记-整理

过程分为两个阶段：

阶段 A：并发标记（与应用线程并发执行，不 STW）
  ① 初始标记（STW，很快）：标记 GC Roots 直接关联的对象
  ② 并发标记：遍历整个对象图，标记存活对象
  ③ 最终标记（STW，较短）：处理 SATB 队列
  ④ 筛选回收：统计每个 Region 的垃圾回收价值（回收空间 / 回收时间）
     → 按价值排序，选出"垃圾最多"的 Region

阶段 B：Mixed GC（STW）
  ⑤ 回收所有新生代 Region（复制存活对象）
  ⑥ 回收部分老年代 Region（标记-整理，移动存活对象）
  ⑦ 恢复应用线程

"G1"名字的由来：
  在第 ④ 步，G1 优先选择回收价值最高的 Region
  即：垃圾最多的 Region 优先回收（Garbage First）
  在有限的停顿时间内，回收最多的垃圾
```

### 3. Full GC（降级回收）

```
触发条件：Mixed GC 回收速度跟不上对象分配速度
  或 Humongous Region 分配失败
  或元空间不足

回收范围：整个堆
算法：标记-整理

过程：
  ① STW
  ② 标记所有存活对象
  ③ 整理：移动存活对象到一端
  ④ 清空另一端
  ⑤ 恢复应用线程

特点：
  - 性能最差，停顿时间最长
  - 是 G1 的"保底方案"，调优目标是尽量避免
  - JDK 10 之前单线程，JDK 10+ 改为多线程并行
```

## 四、Remember Set（RSet）

### 为什么需要 RSet？

```
传统分代收集器：
  老年代对象引用新生代对象 → 用 Card Table 记录
  Card Table 很小，开销可忽略

G1 的问题：
  Region 之间可能互相引用（A Region 的对象引用 B Region 的对象）
  回收某个 Region 时，怎么知道有没有其他 Region 引用它？
  难道要扫描整个堆？→ 太慢

解决方案：Remember Set（RSet）
  每个 Region 维护一个 RSet
  记录"哪些其他 Region 引用了我这个 Region 中的对象"
```

### RSet 工作原理

```
例如：
  Region A 中的对象引用了 Region B 中的对象
  → Region B 的 RSet 中记录："Region A 引用了我"
  → 回收 Region B 时，只需扫描 RSet，不用扫描整个堆
```

### RSet 的开销

```
每个 Region 的 RSet 约占该 Region 大小的 5~20%
总 RSet 开销约占堆的 10~20%
这是 G1 内存占用比 CMS 高的主要原因

RSet 的维护：
  每次写入引用时，通过 Write Barrier 更新 RSet
  写操作有一定的性能开销（约 5~10%）
```

## 五、SATB（Snapshot-At-The-Beginning）

```
G1 并发标记时使用 SATB 算法（而非 CMS 的增量更新）

SATB 的核心思想：
  在标记开始时，给整个堆拍一个"快照"
  标记过程中，如果应用线程修改了引用关系
  → 把旧的引用记录到 SATB 队列中
  → 标记结束后，处理 SATB 队列中的引用
```

### SATB 举例

```
标记开始时：A → B → C（B 和 C 都被标记为存活）

标记过程中：A 不再引用 B，改为引用 D
  → SATB 队列记录："A 曾经引用 B"

最终标记阶段：
  重新扫描 SATB 队列
  → 确保 B 不会因为"引用断开"而被误回收

为什么用 SATB 而不是 CMS 的增量更新？
  SATB 效率更高，不需要在并发标记阶段反复修正
  但 SATB 会产生"浮动垃圾"（标记期间新变成垃圾的对象留到下次回收）
```

## 六、停顿时间预测模型

```
G1 的核心能力：预测停顿时间，选择最优回收策略

原理：
  ① 维护每个 Region 的历史回收数据
     - 回收该 Region 需要多少时间
     - 回收该 Region 能释放多少空间
  ② 根据 -XX:MaxGCPauseMillis 目标
  ③ 选择"在目标时间内能回收最多垃圾"的 Region 集合
```

### 预测举例

```
目标停顿 200ms

Region A：回收耗时 50ms，释放 10MB
Region B：回收耗时 80ms，释放 20MB
Region C：回收耗时 30ms，释放 5MB
Region D：回收耗时 100ms，释放 30MB

G1 选择：A + B + C = 160ms，释放 35MB（在 200ms 内收益最大）
不选 D：单独回收 D 需要 100ms，但性价比不如 A+B+C
```

## 七、Humongous Region（大对象处理）

```
大对象定义：对象大小 > Region 大小的 50%
  例如 Region = 4MB，对象 > 2MB 就是大对象

大对象处理流程：
  ① 直接分配到连续的 Humongous Region 中
  ② H Region 属于老年代（逻辑上）
  ③ H Region 中的对象不参与复制（太大，复制开销高）
  ④ H Region 在 Mixed GC 中被回收（如果对象已死）
     但不会被整理（不移动），可能产生碎片
```

### Humongous Region 的问题

```
大量大对象 → H Region 碎片化
  → 碎片积累 → 无法分配新的大对象
  → 触发 Full GC 来整理碎片

调优建议：
  大对象多时，增大 Region 大小（-XX:G1HeapRegionSize）
  减少大对象被判定为 Humongous 的概率
```

## 八、G1 调优关键参数

| 参数 | 说明 | 默认值 |
|------|------|--------|
| `-XX:+UseG1GC` | 启用 G1 | JDK 9+ 默认 |
| `-XX:MaxGCPauseMillis` | 目标最大停顿时间 | 200ms |
| `-XX:G1HeapRegionSize` | Region 大小 | 自动（1~32MB） |
| `-XX:InitiatingHeapOccupancyPercent` | 触发并发标记的堆占用比 | 45% |
| `-XX:G1NewSizePercent` | 新生代占比下限 | 5% |
| `-XX:G1MaxNewSizePercent` | 新生代占比上限 | 60% |
| `-XX:ParallelGCThreads` | STW 阶段的并行线程数 | CPU 核心数 |
| `-XX:ConcGCThreads` | 并发标记阶段的线程数 | ParallelGCThreads / 4 |

## 九、G1 完整 GC 时间线

```
应用运行
  ↓
Eden Region 填满 → Young GC（STW，20~100ms）
  ↓ 重复多次 Young GC
老年代占用达到 45%（IHOP）
  ↓
并发标记开始（不 STW）
  ├── 初始标记（STW，很短）
  ├── 并发标记（不停顿，与应用并发）
  ├── 最终标记（STW，较短，处理 SATB 队列）
  └── 筛选回收（统计各 Region 价值）
  ↓
Mixed GC 开始（STW）
  ├── 回收所有新生代 Region
  └── 回收"价值最高"的部分老年代 Region
  ↓ 重复多次 Mixed GC（每轮回收一批老年代 Region）
老年代空间充足 → Mixed GC 停止
  ↓
回到正常 Young GC 循环...
  ↓
如果 Mixed GC 跟不上 → Full GC（降级，尽量避免）
```

## 十、G1 的优缺点总结

### 优点

- **停顿时间可预测**：通过 `-XX:MaxGCPauseMillis` 设定目标，G1 智能选择回收策略
- **无内存碎片**：Region 内用复制算法，Mixed GC 用标记-整理
- **整堆管理**：不需要像 CMS 那样配合 ParNew，调优更简单
- **支持大堆**：几十 GB 的堆也能保持可控的停顿时间
- **JDK 10+ 并行 Full GC**：Full GC 从单线程变多线程

### 缺点

- **内存占用高**：RSet 记录跨 Region 引用，总开销约占堆的 10~20%
- **Full GC 性能差**：JDK 10 之前是单线程，触发 Full GC 停顿可能达数秒
- **停顿时间"软保证"**：`MaxGCPauseMillis` 只是目标，高负载时可能超标
- **不适合小堆**：堆 < 2GB 时 Region 太小，RSet 开销占比更高
- **大对象处理局限**：H Region 不能移动，大量大对象时产生碎片

---

## 一句话总结

> G1 的核心创新是 **Region 化 + 价值驱动的混合回收**：把堆划分为等大 Region，通过 RSet 追踪跨 Region 引用，用 SATB 实现高效并发标记，最终在有限的停顿时间内**优先回收垃圾最多的 Region**（Garbage First）。Young GC 回收新生代，Mixed GC 混合回收新生代 + 部分老年代，Full GC 是降级保底方案。
