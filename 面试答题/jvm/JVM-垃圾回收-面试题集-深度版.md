## 第 1 题：如何判断对象是否死亡（两种方法）

### 题目

**请介绍 Java 中判断对象是否可回收的两种方法，各自的优缺点是什么？Java 为什么选择了可达性分析？**

### 深度回答

**① 引用计数法**：每个对象维护一个引用计数器，被引用 +1，引用断开 -1，为 0 时判定为死亡。优点是简单高效，无需 STW 暂停；缺点是**无法解决循环引用**——A 引用 B，B 引用 A，两者计数都不为 0，但实际已不可达。Python 用引用计数 + 循环引用检测机制，Swift 用引用计数 + 手动弱引用打破循环，Java **不使用**此方法。

**② 可达性分析（Java 采用）**：从一组 GC Roots 出发，沿引用链向下搜索。能到达的对象标记为存活，不能到达的标记为可回收。**天然解决循环引用**——即使 A 和 B 互相引用，只要都无法从 GC Roots 到达，就会被正确回收。

**为什么 Java 选择可达性分析？** Java 的对象图非常复杂（框架中大量双向引用、观察者模式、缓存持有等），循环引用极其常见。如果用引用计数，要么像 Python 那样额外维护循环检测机制（复杂度高），要么像 Swift 那样引入弱引用手动打破循环（增加开发者负担）。可达性分析虽然需要 STW 暂停，但配合并发标记（CMS/G1/ZGC），停顿已经可以做到很低。

**GC Roots 包括**：
- 虚拟机栈中引用的对象（局部变量）
- 静态变量引用的对象
- 常量引用的对象（字符串常量池等）
- Native 方法引用的对象（JNI）

## 第 2 题：四种引用类型及软引用的好处

### 题目

**简单介绍强引用、软引用、弱引用、虚引用。虚引用与软引用和弱引用的区别是什么？使用软引用能带来什么好处？**

### 深度回答

**强引用**：`Object obj = new Object()`，GC 绝不回收，宁可 OOM。是 Java 内存泄漏的根源——静态 Map 不 remove、监听器不注销、ThreadLocal 不清理都是强引用导致的。

**软引用**（SoftReference）：内存不足时才回收，内存充足时和强引用一样不回收。

**弱引用**（WeakReference）：不管内存够不够，下次 GC 就回收。用于"有了更好，没有也行"的场景。

**虚引用**（PhantomReference）：随时回收，`get()` 永远返回 null。

**虚引用与软/弱引用的本质区别**：软引用和弱引用的目的是"延迟回收"（内存不足时/下次 GC 时），可以通过 `get()` 获取对象；而虚引用的目的不是延迟回收，而是**跟踪对象被回收的时机**——对象被回收时虚引用会被放入 ReferenceQueue，可以据此执行资源清理。

**软引用的好处**：实现**内存敏感的缓存而不 OOM**——比如图片缓存、页面缓存、解析结果缓存，内存充足时缓存生效加速访问，内存紧张时自动释放避免崩溃，**无需手动管理缓存大小和淘汰策略**。JDK 还会根据 `-XX:SoftRefLRUPolicyMSPerMB` 参数按 LRU 策略决定哪些软引用先回收，不是所有软引用一次性全部回收。

**四种引用对比**：

| 引用类型 | GC 行为 | `get()` 返回值 | 典型用途 |
|---------|---------|---------------|---------|
| **强引用** | 永不回收 | 始终有值 | 普通对象 |
| **软引用** | 内存不足时回收 | 可能为 null | 缓存（图片、页面） |
| **弱引用** | 下次 GC 必回收 | 可能为 null | ThreadLocal、WeakHashMap、监听器 |
| **虚引用** | 随时回收 | **永远返回 null** | 跟踪回收时机、堆外内存释放 |

**实战补充**：业务代码中几乎不直接使用软/弱/虚引用，但它们广泛存在于框架底层——ThreadLocal 的 key 是弱引用，NIO DirectByteBuffer 用虚引用 + Cleaner 释放堆外内存，Guava Cache 内部支持软引用实现自动过期。面试时可以从"间接使用"的角度展示深度理解。

## 第 3 题：如何判断一个常量是废弃常量

### 题目

**运行时常量池中的常量在什么情况下会被回收？如何判断一个常量是废弃常量？**

### 深度回答

以字符串常量池为例，判断条件是**该常量是否还有任何强引用指向它**。

```java
String s = "hello";  // "hello" 进入常量池，被 s 强引用
s = null;            // 强引用断开
// 如果没有任何其他引用指向常量池中的 "hello"
// 该常量被标记为废弃，可被 GC 回收
```

在 GC 的标记阶段，从 GC Roots 出发遍历引用链，常量池中的常量如果没有被任何存活的对象、类、ClassLoader 引用，就会被标记为可回收。**类卸载时会连带卸载其运行时常量池**，对应的字符串常量如果没有其他引用也会被回收。

**什么场景会产生废弃常量？** 大量使用 `String.intern()` 动态添加字符串到常量池，但后续不再使用。比如日志处理中对每条日志做 intern，日志处理完后这些字符串就成了废弃常量。JDK 1.7+ 常量池在堆中，废弃常量可被 Minor GC 回收——这也是常量池从永久代替移到堆中的好处之一（永久代的废弃常量很难被回收）。

## 第 4 题：如何判断一个类是无用的类

### 题目

**什么情况下一个类会被卸载？需要满足哪些条件？**

### 深度回答

HotSpot 要求**同时满足以下三个条件**，类才会被判定为无用类并被卸载：

1. **该类所有实例都已被回收**：堆中不存在该类的任何实例对象
2. **加载该类的 ClassLoader 已被回收**：该 ClassLoader 没有任何引用
3. **该类的 `java.lang.Class` 对象没有被任何地方引用**：没有通过反射、静态变量等方式持有该 Class 对象

三个条件**缺一不可**。满足后，类会在 Full GC 或 G1 的并发标记阶段被卸载，对应的元空间内存被释放。

**实战场景**：热部署/热加载场景中，每次重新加载都会创建新的 ClassLoader 和新的类。如果旧的 ClassLoader 没有正确释放（被静态变量、ThreadLocal 等持有），旧类就永远无法卸载，最终导致 `OOM: Metaspace`。解决方案：确保旧 ClassLoader 的所有引用都被清除，可通过 `-XX:+TraceClassUnloading` 监控类卸载情况。

## 第 5 题：垃圾收集算法及各自特点

### 题目

**垃圾收集有哪些算法？各自的特点和适用场景是什么？**

### 深度回答

**标记-清除**：先标记存活对象，再清除未标记对象。优点是实现简单；缺点是产生**内存碎片**，碎片积累后无法分配大对象，触发 Full GC。CMS 使用此算法。

**标记-复制**：将内存分为两块，GC 时把存活对象复制到另一块。优点是**无碎片、分配极快**（指针碰撞）；缺点是浪费一半空间。新生代使用此算法，但做了优化——不是 1:1 划分，而是 Eden(8):S0(1):S1(1)，因为新生代对象存活率极低（<2%），浪费的空间远不到一半。

**标记-整理**：标记存活对象后，将它们向一端移动，清空另一端。优点是**无碎片、不浪费空间**；缺点是移动对象需要更新所有引用，开销大。Serial Old 和部分老年代收集器使用。

**分代收集**：不是独立算法，而是根据对象存活周期**组合使用**上述算法——新生代用复制（朝生夕灭，存活率低），老年代用标记-清除或标记-整理（存活率高）。这是 HotSpot 实际采用的策略。

**面试加分点**：G1 的算法是**分区复制 + 标记整理**的混合体——每个 Region 内部用复制算法（Young GC），跨 Region 用标记整理（Mixed GC），兼顾了低碎片和可预测停顿。

## 第 6 题：HotSpot 为什么要分为新生代和老年代？

### 题目

**为什么 HotSpot 要将堆分为新生代和老年代？如果不分代会怎样？**

### 深度回答

**根本原因：不同生命周期的对象，最优回收策略完全不同。**

基于**弱代假说**（Weak Generational Hypothesis）：绝大多数对象都是朝生夕灭的（>98% 在第一次 GC 时就被回收），只有极少数对象能长期存活。

- **新生代**：用复制算法，因为存活率低，每次只需复制少量存活对象，大部分内存直接清空，效率极高。如果用标记-清除，大量碎片会严重影响分配性能。
- **老年代**：用标记-整理/清除，因为存活率高，复制成本太高（要复制大量存活对象）。而且老年代对象生命周期长，碎片产生速度慢。

**如果不分代会怎样？** 所有对象混在一起，GC 时必须扫描整个堆。存活对象多时复制开销巨大，不分代的早期 JVM 就是这样，性能远不如分代收集。

**G1 的特殊之处**：G1 虽然也分代，但不再是物理上固定的两个区域，而是通过 Region 逻辑分代——Region 可以动态标记为 Eden/Survivor/Old，更灵活。

## 第 7 题：常见的垃圾回收器有哪些？

### 题目

**请列举 HotSpot 中常见的垃圾回收器，以及各自的特点和适用场景。**

### 深度回答

| 收集器 | 区域 | 算法 | 线程 | 停顿 | 吞吐量 | 适用场景 |
|--------|------|------|------|------|--------|---------|
| **Serial** | 新生代 | 复制 | 单线程 | 高 | 低 | 客户端、小内存 |
| **ParNew** | 新生代 | 复制 | 多线程 | 中 | 中 | 配合 CMS |
| **Parallel Scavenge** | 新生代 | 复制 | 多线程 | 中 | **高** | JDK 8 默认 |
| **Serial Old** | 老年代 | 整理 | 单线程 | 高 | 低 | CMS 后备 |
| **CMS** | 老年代 | 清除 | 并发 | **低** | 中 | 低延迟（JDK 17 已移除） |
| **Parallel Old** | 老年代 | 整理 | 多线程 | 中 | **高** | JDK 8 默认 |
| **G1** | 整堆 | 分区复制+整理 | 并发 | 可预测 | 中高 | **JDK 9+ 默认** |
| **ZGC** | 整堆 | 着色指针 | 并发 | **< 1ms** | 中 | 极致低延迟 |
| **Shenandoah** | 整堆 | 并发压缩 | 并发 | **< 10ms** | 中 | 低延迟（x86） |

**选择建议**：JDK 8 用 Parallel（默认）或 ParNew+CMS（低延迟），JDK 17+ 用 G1（通用）或 ZGC（低延迟），JDK 21+ 用 ZGC Generational。

## 第 8 题：CMS 和 G1 收集器

### 题目

**请分别介绍 CMS 和 G1 收集器的工作原理，并对比它们的优缺点。**

### 深度回答

**CMS（Concurrent Mark Sweep）**：以最短停顿为目标的老年代收集器。

四个阶段：
- ① **初始标记**（STW，很快）：仅标记 GC Roots 直接关联的对象
- ② **并发标记**（不停顿）：从 GC Roots 出发遍历整个对象图
- ③ **重新标记**（STW，较短）：修正并发标记期间因用户线程运行导致的标记变动
- ④ **并发清除**（不停顿）：清除未标记对象

缺点：有**内存碎片**（标记-清除不压缩）、**浮动垃圾**（并发清除阶段新产生的垃圾留到下次）、CPU 敏感、最致命的 **Concurrent Mode Failure**（老年代空间不足时退化为 Serial Old，停顿暴涨）。JDK 17 已被彻底移除。

**G1（Garbage First）**：将整个堆划分为约 2048 个等大 Region（1~32MB），每个 Region 动态充当 Eden/Survivor/Old/Humongous。

三种 GC：
- **Young GC**：回收所有新生代 Region，STW
- **Mixed GC**：回收新生代 + 部分老年代 Region，"Garbage First"优先回收垃圾最多的 Region
- **Full GC**：降级，单线程（JDK 10+ 多线程），要尽量避免

**核心区别**：

| | CMS | G1 |
|--|-----|-----|
| 管理范围 | 只管老年代 | 管理整个堆 |
| 碎片 | 有（标记-清除） | 无（Region 内复制） |
| 停顿 | 不可控 | 可预测（MaxGCPauseMillis） |
| 内存开销 | 低 | 高（RSet 10~20%） |
| 配合 | 需配合 ParNew | 独立管理整堆 |

## 第 9 题：Minor GC 和 Full GC 的区别

### 题目

**Minor GC 和 Full GC 有什么不同？Full GC 在什么情况下会被触发？**

### 深度回答

| | Minor GC | Full GC |
|--|---------|---------|
| **回收区域** | 仅新生代（Eden + Survivor） | 整个堆（新生代 + 老年代）+ 元空间 |
| **触发条件** | Eden 区空间不足 | 老年代不足 / 元空间不足 / System.gc() |
| **频率** | 非常频繁 | 较少 |
| **速度** | 快（新生代小，大部分对象直接回收） | 慢（老年代大，存活对象多） |
| **停顿时间** | 短（通常 10~100ms） | 长（可能几百 ms 到几秒） |
| **算法** | 复制算法 | 标记-整理/清除 |

**触发 Full GC 的五种场景**：
1. **老年代空间不足**：对象晋升过多或大对象直接进入
2. **元空间不足**：动态加载类过多（CGLIB、热部署）
3. **显式调用** `System.gc()`（建议性，不保证执行）
4. **CMS Concurrent Mode Failure**：老年代空间跟不上分配速度
5. **G1 Mixed GC 跟不上**：回收速度赶不上分配速度，降级为 Full GC

**调优目标**：尽量减少 Full GC 频率。如果 Full GC 频繁，首先检查是否有内存泄漏（MAT 分析 heap dump），其次检查新生代是否太小导致对象过早晋升老年代，最后检查是否有大量大对象直接进入老年代。

## 第 10 题：G1 / ZGC / Shenandoah 各有什么缺点？

### 题目

**G1、ZGC、Shenandoah 各有什么缺点？既然有缺点为什么还要从 CMS/G1 升级？**

### 深度回答

**G1 缺点**：RSet 内存开销 10~20%、停顿是"软保证"可能超标、Full GC 性能差（JDK 10 前单线程）、不适合小堆（< 2GB）、大对象 H Region 不能移动可能产生碎片。

**ZGC 缺点**：读屏障增加 5~15% CPU 开销、吞吐量下降 10~20%、内存额外开销 10~25%、JDK 21 前不支持分代、社区生态不如 G1。

**Shenandoah 缺点**：仅支持 x86_64（不支持 ARM）、Brooks Pointer 每个对象头 +8 字节、写屏障导致吞吐量下降 15~30%、Red Hat 主导 Oracle 支持有限。

**为什么还要升级？** 因为"缺点"是相对的，关键看痛点：

| 升级路径 | 代价 | 收益 | 结论 |
|---------|------|------|------|
| CMS → G1 | 多占 10~20% 内存 | 无碎片 + 停顿可预测 | **值**，内存便宜，稳定性无价 |
| G1 → ZGC | 多花 10~15% CPU | 停顿从 100ms 降到 < 1ms | **值**（低延迟场景），确定性延迟比 CPU 重要 |

**GC 调优的"不可能三角"**：低停顿、高吞吐、低内存只能选两个。升级不是追求完美，而是在你的场景下选择最优解。

**什么时候不值得升级？** 堆 < 4GB 用 Parallel 就够；CPU 已打满不要上 ZGC；JDK 8 老项目短期不升级继续用 CMS/G1。

## 第 11 题：对象进入老年代有哪些条件？

### 题目

**对象在什么情况下会从新生代晋升到老年代？请详细解释每个条件。**

### 深度回答

三个条件，满足任意一个即晋升：

**条件一：年龄达到阈值（默认 15）**。对象每次在 Minor GC 中存活，年龄 +1。经历 15 次 GC 还存活说明是"长寿对象"，放在新生代反复复制反而浪费。默认 15 是因为对象头中分代年龄只有 4 bit，最大值就是 15。可通过 `-XX:MaxTenuringThreshold` 调整。

**条件二：动态年龄判断**。不看单个对象的年龄，看同龄对象的总量。如果 Survivor 区中，某个年龄及以下的所有对象总大小 > Survivor 空间的一半，那么大于等于该年龄的对象全部直接进入老年代，不用等到 15 岁。设计目的是 Survivor 空间有限时，自动让年龄较大的对象提前进入老年代，给新对象腾出空间。

**条件三：大对象直接进入老年代**。大对象在新生代来回复制太浪费（每次 Minor GC 复制 10MB，复制 15 次 = 150MB 复制开销），直接放老年代用标记-整理算法，零复制开销。通过 `-XX:PretenureSizeThreshold` 控制，但只对 Serial 和 ParNew 生效。G1 有专门的 Humongous Region，对象 > Region 50% 时自动放入。

## 第 12 题：JDK 17/21 的 GC 有什么新变化？

### 题目

**JDK 17 和 JDK 21 在垃圾回收方面有哪些重要变化？**

### 深度回答

**JDK 17（2021，LTS）**：
- **CMS 彻底移除**（JEP 363）：`-XX:+UseConcMarkSweepGC` 会直接报错，低延迟场景改用 ZGC 或 Shenandoah
- **ZGC 正式生产可用**（JEP 377）：停顿 < 1ms，支持几 MB 到几 TB 的堆，用着色指针 + 读屏障实现全程并发
- **Shenandoah 正式生产可用**（JEP 379）：Red Hat 开发，类似 ZGC 但仅支持 x86_64
- **G1 并行 Full GC**（JEP 307）：Full GC 从单线程变多线程，大幅减少 Full GC 停顿

**JDK 21（2023，LTS）**：
- **ZGC 分代模式**（JEP 439）：`-XX:+UseZGC -XX:+ZGenerational`，新生代单独回收更频繁更快，吞吐量比非分代 ZGC 提升 20%+
- **虚拟线程影响 GC**（JEP 444）：数百万虚拟线程导致 GC Roots 扫描范围更大，ZGC/Shenandoah 的并发标记比 G1 更适合虚拟线程场景

**演进趋势**：G1 从 JDK 9 至今一直是默认 GC，但 ZGC Generational 正在成为下一代推荐方案，JDK 25 可能将 ZGC 作为默认 GC。
