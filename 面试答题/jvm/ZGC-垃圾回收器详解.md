# ZGC 垃圾回收器详解

---

## 一、核心目标

> **停顿时间 < 1ms，且与堆大小无关**——无论是 8MB 还是 16TB 的堆，停顿时间都一样。

传统 GC 的停顿时间随堆增大而增加（堆越大，标记/复制/整理越慢）。ZGC 通过**将几乎所有 GC 工作都与应用线程并发执行**，只在极短的关键点 STW，实现了这个目标。

---

## 二、两大核心技术

### 1. 着色指针（Colored Pointers）

**核心思想**：把 GC 标记信息直接存在指针本身中，而不是额外的数据结构。

```
64 位指针的布局（ZGC 着色指针）：

┌──────────────────────────────────────────────────┐
│  元数据位（4 bit）  │      对象地址（42 bit）        │
│  Marked0/Marked1/  │   （最大支持 4TB 堆）          │
│  Remapped/Finalizable│                              │
└──────────────────────────────────────────────────┘
  ↑                                    ↑
GC 标记信息直接存在指针中        实际的对象地址

传统 GC：需要额外的标记位图（Mark Bitmap）
  → 每个对象至少 1 bit 的额外内存
  → 堆越大，位图越大

ZGC：标记信息直接存在指针中
  → 不需要额外的标记位图
  → 内存开销更低
```

**四个元数据位的含义**：

| 位 | 名称 | 含义 |
|---|------|------|
| bit 0 | Marked0 | 标记阶段第一轮标记 |
| bit 1 | Marked1 | 标记阶段第二轮标记 |
| bit 2 | Remapped | 重定位后，指针已更新到新地址 |
| bit 3 | Finalizable | 对象只能通过弱/软/虚引用到达（待 finalize） |

### 2. 读屏障（Load Barrier）

**核心思想**：每次从堆中读取对象引用时，拦截并检查指针的颜色位。

```java
Object ref = someObject.field;  // 读取引用时触发读屏障
```

```
读屏障的执行流程：

① 从堆中读取引用 ref
② 检查 ref 的颜色位
③ 如果颜色位表示"这个指针需要修复"
   → 自动修复指针（更新到新地址）
④ 返回修复后的引用给应用代码

为什么需要读屏障？
  ZGC 在并发转移对象时，对象被移动到新地址
  但应用线程可能还持有旧地址的引用
  → 读屏障在读取时自动修复，保证应用拿到正确的地址
```

**读屏障的开销**：
```
每次读取引用都要经过读屏障检查
  → 增加约 5~15% 的 CPU 开销
  → 这是 ZGC 吞吐量下降的主要原因

对比：
  传统 GC（STW）：转移对象时暂停应用，不需要读屏障
  ZGC（并发）：转移对象时应用在运行，需要读屏障修复指针
```

## 三、ZGC 的 GC 过程

ZGC 的 GC 周期分为多个阶段，**只有两个阶段需要 STW**，且都非常短：

```
ZGC 完整 GC 周期：

① 暂停标记开始（STW）        ← 极短，< 1ms
   ↓
② 并发标记                    ← 不停顿
   ↓
③ 暂停标记结束（STW）        ← 极短，< 1ms
   ↓
④ 并发准备重定位              ← 不停顿
   ↓
⑤ 并发重定位                  ← 不停顿
   ↓
⑥ 并发引用处理                ← 不停顿

只有 ① 和 ③ 需要 STW，且都在 1ms 以内
其余阶段全部与应用线程并发执行
```

### 各阶段详解

#### ① 暂停标记开始（STW，< 1ms）

```
做三件事：
  ① 扫描 GC Roots（栈中引用、静态变量等）
  ② 将所有 GC Roots 直接引用的对象标记为存活
  ③ 启用 SATB 写屏障（记录后续引用变化）

为什么快？
  只扫描 GC Roots 直接引用的对象（一层），不遍历整个对象图
  GC Roots 数量通常很少（几百到几千个），扫描极快
```

#### ② 并发标记（不停顿）

```
从已标记的对象出发，遍历整个对象图
标记所有可达对象为存活

与应用线程并发执行：
  - 应用线程在修改对象引用
  - SATB 写屏障记录引用变化
  - 标记线程根据记录修正标记结果

使用着色指针的 Marked0/Marked1 位记录标记状态
不需要额外的标记位图
```

#### ③ 暂停标记结束（STW，< 1ms）

```
做三件事：
  ① 处理 SATB 队列中的引用变化
  ② 处理弱引用、软引用、虚引用
  ③ 选择需要重定位的 Region

为什么快？
  SATB 队列通常很小（并发标记期间引用变化不多）
  引用处理也是增量式的
```

#### ④ 并发准备重定位（不停顿）

```
构建重定位集合（Relocation Set）：
  选择碎片化严重的 Region 作为重定位目标
  计算每个对象的新地址

不需要 STW，因为只是"计划"，还没有真正移动对象
```

#### ⑤ 并发重定位（不停顿）— ZGC 的核心创新

```
将存活对象从旧 Region 复制到新 Region
同时应用线程在运行！

关键问题：应用线程可能正在读写正在被移动的对象

解决方案：读屏障 + 转发表
  - 对象被移动后，旧地址保留一个"转发指针"指向新地址
  - 应用线程通过读屏障读取引用时，自动跟随转发指针到新地址
  - 写操作通过写屏障更新到新地址

对比传统 GC：
  CMS/G1：移动对象时必须 STW，暂停应用
  ZGC：移动对象时应用在运行，通过读屏障自动修复指针
```

#### ⑥ 并发引用处理（不停顿）

```
扫描堆中所有引用，更新指向旧地址的引用为新地址
完成后，旧 Region 可以整体释放
```

## 四、ZGC 的内存布局

```
ZGC 不使用分代（JDK 21 之前）
整个堆是一个整体，不区分新生代/老年代

堆布局：
┌──────────────────────────────────────────┐
│  ZGC 堆（整体管理）                       │
│  ┌────────┬────────┬────────┬────────┐  │
│  │Region 0│Region 1│Region 2│Region N│  │
│  └────────┴────────┴────────┴────────┘  │
│                                          │
│  每个 Region 大小相等（默认 2MB 或 4MB）   │
└──────────────────────────────────────────┘

JDK 21 分代 ZGC：
  -XX:+UseZGC -XX:+ZGenerational
  引入逻辑分代，新生代和老年代分别回收
  吞吐量提升 20%+
```

## 五、ZGC 与 G1/CMS 的核心区别

| | CMS | G1 | ZGC |
|--|-----|-----|-----|
| **STW 阶段** | 初始标记 + 重新标记 | Young GC + Mixed GC | 仅标记开始/结束（< 1ms） |
| **转移对象** | 不转移（无压缩） | STW 时转移 | **并发转移**（应用在运行） |
| **碎片处理** | 不处理，有碎片 | Region 内复制，无碎片 | 并发重定位，无碎片 |
| **标记信息存储** | 额外位图 | 额外位图 | **着色指针**（无额外位图） |
| **指针修复** | 不需要 | STW 时更新 | **读屏障**（并发修复） |
| **停顿时间** | 几十~几百 ms | 几十~200ms | **< 1ms** |

## 六、调优参数

| 参数 | 说明 | 默认值 |
|------|------|--------|
| `-XX:+UseZGC` | 启用 ZGC | JDK 15+ |
| `-XX:+ZGenerational` | 启用分代 ZGC（JDK 21+） | 关闭 |
| `-XX:SoftMaxHeapSize` | 软堆上限（ZGC 尽量不超此值） | 无 |
| `-XX:ConcGCThreads` | 并发 GC 线程数 | CPU 核心数 / 4 |
| `-XX:ZCollectionInterval` | 强制 GC 间隔（ms） | 0（不强制） |

## 七、优缺点

### 优点

- **停顿 < 1ms**：与堆大小无关，8MB 和 16TB 停顿一样
- **无碎片**：并发重定位消除碎片
- **支持超大堆**：从几 MB 到几 TB
- **内存效率高**：着色指针不需要额外标记位图

### 缺点

- **CPU 开销大**：读屏障增加 5~15% CPU 开销，吞吐量下降 10~20%
- **内存额外开销**：转发表 + 并发数据结构，约 10~25%
- **JDK 21 前无分代**：整堆收集效率不如分代（JDK 21 已解决）
- **社区生态不如 G1**：调优经验和监控工具较少

---

## 八、一句话总结

> ZGC 通过**着色指针**（把标记信息存在指针中）和**读屏障**（读取引用时自动修复指针）两大技术，实现了**并发转移对象**（移动对象时应用线程在运行）。整个 GC 周期只有两个 STW 阶段（标记开始和结束），且都在 1ms 以内。代价是读屏障带来 5~15% 的 CPU 开销和 10~20% 的吞吐量下降，但对于延迟敏感型应用来说，确定性的 < 1ms 停顿远比吞吐量更重要。
