# 对象创建过程 - 面试题集（深度版）

---

## 第 1 题：对象创建流程

### 题目

**请描述 HotSpot 1.8 中，执行 `new User("张三")` 时，JVM 底层经历了哪些步骤，从字节码被解释执行开始，到对象最终可用为止？**

---

### 深度回答

> **① 类加载检查**：JVM 遇到 `new` 指令时，首先检查 `User` 类是否已加载到元空间。未加载则触发完整的类加载流程（加载 → 验证 → 准备 → 解析 → 初始化）。类加载有**双亲委派机制**保证同一个类不会被重复加载，所以只有第一次 `new` 时有开销，后续全部跳过。
>
> **② 分配内存**：在堆的 **Eden 区**分配，不是"根据类型随便找个地方"。内存分配有两种方式：**指针碰撞**（Serial/ParNew GC，内存规整时移动指针即可）和**空闲列表**（CMS GC，内存碎片化时需要查找空闲块）。多线程并发分配时，HotSpot 默认优先使用 **TLAB**（每个线程预分配私有缓冲区，无锁），TLAB 满了才走 **CAS + 失败重试**。大对象（超过 TLAB 容量）直接跳过 TLAB 走 CAS。
>
> **③ 零值初始化**：将对象内存（不含对象头）全部置为零值。**基本类型为 0/false，引用类型为 null**。这里有个关键点：嵌套对象（如 `private Address address = new Address()`）在此阶段**只有 null 引用**，Address 对象根本还没创建，它要等到步骤 ⑤ 执行字段初始化时才被 new 出来。
>
> **④ 设置对象头**：写入 **Mark Word**（8 字节：hashCode、GC 分代年龄、锁状态标志、偏向线程 ID）和 **Klass Pointer**（4 字节，开启指针压缩，指向元空间中该类的元信息）。数组对象还额外写入 4 字节的数组长度。hashCode 是**延迟计算**的，第一次调用 `hashCode()` 时才生成并写入 Mark Word。
>
> **⑤ 执行 `<init>`**：完整顺序是**父类构造方法 → 字段声明赋值 → 实例代码块 → 构造方法体**。字段赋值和实例代码块按源码书写顺序交叉执行。嵌套对象在此阶段通过 `new` 创建。
>
> **⑥ 返回引用**：将对象地址赋给栈中的局部变量，对象创建完成。
>
> **实战补充**：在高并发场景下，对象分配的瓶颈主要在步骤 ②，这也是 TLAB 存在的意义——用**空间换时间**避免锁竞争。可以通过 `-XX:+PrintTLABAllocation` 观察 TLAB 使用情况，如果发现 TLAB 浪费严重（线程多但每个线程分配少），可以调整 `-XX:TLABWasteTargetPercent`。

## 第 2 题：TLAB 与 CAS 的协作机制

### 题目

**多线程环境下，HotSpot 如何保证对象内存分配的线程安全？请详细描述 TLAB 的工作机制，以及大对象（如 `new byte[1024*1024]`）是如何处理的？**

---

### 深度回答

> **TLAB（Thread Local Allocation Buffer）** 本质是**用空间换时间**的并发优化策略。每个线程在 Eden 区预分配一块私有缓冲区（默认约 Eden 的 1%，可通过 `-XX:TLABSize` 调整），线程在自己 TLAB 中分配内存**完全无锁**，和单线程一样快。
>
> **完整分配优先级**：
> ```
> TLAB 中分配（首选，无锁，极快）
>     ↓ TLAB 空间不足
> CAS 向 Eden 申请新 TLAB（失败则重试，乐观锁思想）
>     ↓ 对象大小超过 TLAB 容量（大对象）
> 直接 CAS 在 Eden 区分配（跳过 TLAB）
> ```
>
> **大对象处理**：`new byte[1024*1024]`（1MB）远超默认 TLAB 容量（几十 KB），HotSpot 检测到对象大小 > TLAB 剩余空间且 > TLAB 最大容量时，**直接走 CAS 在 Eden 区分配**，不经过 TLAB。更进一步，如果大对象生命周期较长，可以通过 `-XX:PretenureSizeThreshold` 参数让大对象**直接分配到老年代**，避免在 Eden 区频繁触发 Minor GC 和大对象复制开销。
>
> **TLAB 的生命周期**：TLAB 是 Eden 的一部分，不需要单独释放。Eden 满了触发 Minor GC 时，所有旧 TLAB 随 Eden 一起被清空，GC 后各线程重新分配新 TLAB。
>
> **实战坑点**：高线程数场景（如 500+ 线程的 Web 服务），每个线程都预分配 TLAB，可能浪费大量 Eden 空间。我们通过 `-XX:TLABWasteTargetPercent` 控制 TLAB 最大浪费比例（默认 1%），同时监控 `-XX:+PrintTLABAllocation` 日志，最终将线程数控制在合理范围，减少了约 15% 的 Eden 浪费。
>
> **与其他方案的对比**：CAS 是乐观锁，适合**低竞争**场景；如果竞争非常激烈（如秒杀），CAS 反复重试反而消耗 CPU，此时不如加锁。TLAB 的设计就是**尽量避免走到 CAS**，把并发问题在分配前就消解掉。

## 第 3 题：零值初始化与 <init> 执行顺序

### 题目

**以下代码执行 `new Order()` 后，`baseId`、`quantity`、`name`、`address` 四个字段的最终值分别是什么？请按零值初始化阶段和 `<init>` 执行阶段，描述每个字段的值变化过程。**

```java
class BaseOrder {
    private String baseId = "BASE001";
}

public class Order extends BaseOrder {
    private int quantity = 10;
    private String name = "默认订单";
    private Address address = new Address("上海");

    public Order() {
        this.name = "正式订单";
    }
}
```

---

### 深度回答

> **零值初始化阶段**（分配内存后立即执行）：
> - `baseId = null`（引用类型零值）
> - `quantity = 0`（int 零值）
> - `name = null`（引用类型零值）
> - `address = null`（引用类型零值，**Address 对象此时未创建**）
>
> **`<init>` 执行阶段**（按源码顺序）：
>
> | 步骤 | 执行内容 | 字段变化 |
> |------|---------|---------|
> | ① | `super()` 触发 BaseOrder 初始化 | `baseId` → `"BASE001"` |
> | ② | 字段初始化 `quantity = 10` | `quantity` → `10` |
> | ③ | 字段初始化 `name = "默认订单"` | `name` → `"默认订单"` |
> | ④ | 字段初始化 `address = new Address("上海")` | `address` → Address 对象（**此刻才创建**） |
> | ⑤ | 构造方法体 `this.name = "正式订单"` | `name` → `"正式订单"`（覆盖） |
>
> **最终值**：`baseId = "BASE001"`、`quantity = 10`、`name = "正式订单"`、`address = Address 对象`
>
> **关键细节**：`name` 被赋值了**两次**，字段初始化的 "默认订单" 被构造方法体的 "正式订单" 覆盖。如果构造方法体中写的是 `this.name = name`（参数），容易因为**字段遮蔽**导致 bug。
>
> **实战坑点：构造方法中调用可被子类重写的方法是危险操作**
>
> 这是 Java 中经典的“构造方法中调用虚方法”陷阱。Effective Java 第 19 条明确建议：**构造方法中不要调用可重写的方法**。
>
> **踩坑案例**：
>
> ```java
> class Parent {
>     public Parent() {
>         init();  // 构造方法中调用可重写方法
>     }
>     protected void init() {
>         System.out.println("Parent init");
>     }
> }
>
> class Child extends Parent {
>     private String name = "张三";
>     private List<String> list = new ArrayList<>();
>
>     @Override
>     protected void init() {
>         System.out.println("name = " + name);  // 输出 null
>         list.add("hello");                     // NullPointerException！
>     }
> }
>
> new Child();
> // 输出：name = null
> // 异常：NullPointerException
> ```
>
> **执行顺序分析**：
>
> ```
> new Child()
>     ↓
> ① 分配内存 + 零值初始化：name = null, list = null
>     ↓
> ② super() → Parent 构造方法
>     ↓
> ③ Parent() 中调用 init()
>    → 多态分发，调用 Child.init()
>    → 此时 Child 字段还是零值：name = null, list = null
>    → list.add() → NullPointerException！
>     ↓
> ④ Child 字段初始化：name = "张三", list = new ArrayList<>()
>    → 太晚了，init() 已经执行完了
> ```
>
> **正确做法**：
> - 方案一：构造方法中不调用可重写方法，改为显式 `init()` 方法由外部调用
> - 方案二：用 `private` 或 `final` 修饰方法，阻止子类重写
> - 方案三：如果必须在构造中初始化，将逻辑放在当前类内部，不依赖子类实现

## 第 4 题：对象头结构详解

### 题目

**请描述 HotSpot 1.8 中对象头（Object Header）的结构，Mark Word 中包含哪些信息？Klass Pointer 指向哪里？数组对象和普通对象的对象头有什么区别？**

---

### 深度回答

> **HotSpot 1.8 对象头结构（64 位 JVM，开启指针压缩，这是默认配置）**：
>
> ```
> 普通对象（共 12 字节）
> ┌──────────────────────────────────────────────────┐
> │ Mark Word（8 字节）                               │
> │  - hashCode（25 bit）：对象哈希码，延迟计算         │
> │  - GC 分代年龄（4 bit，0~15）：超过阈值进入老年代    │
> │  - 锁状态标志（2 bit）：无锁/偏向/轻量/重量         │
> │  - 偏向线程 ID（54 bit）：偏向锁状态下记录独占线程   │
> │  - 偏向时间戳等                                    │
> ├──────────────────────────────────────────────────┤
> │ Klass Pointer（4 字节，开启 UseCompressedOops）    │
> │  → 指向元空间中该类的元信息（InstanceKlass 结构）    │
> └──────────────────────────────────────────────────┘
>
> 数组对象额外多出 4 字节（共 16 字节）
> ┌──────────────────────────────────────────────────┐
> │ 数组长度（4 字节，最大 Integer.MAX_VALUE）          │
> └──────────────────────────────────────────────────┘
> ```
>
> **Klass Pointer 的作用**：JVM 通过它找到类的 `InstanceKlass` 元信息，判断对象是哪个类的实例。`instanceof` 判断、虚方法分发（`invokevirtual`）都依赖它。开启 `-XX:+UseCompressedOops`（默认开启）时为 4 字节，关闭时为 8 字节。
>
> **hashCode 的延迟计算**：hashCode 不是对象创建时就生成的，而是**第一次调用 `hashCode()` 时**才计算并写入 Mark Word。如果对象处于偏向锁/轻量级锁状态，hashCode 会被暂时存到线程栈的**锁记录**中，解锁时写回。
>
> **偏向锁的现状**：偏向锁在 **JDK 15 已被废弃**（JEP 374），原因是现代应用基本都是多线程场景，偏向锁撤销的开销（需要暂停线程、修改对象头）反而比收益更大。JDK 15+ 的锁升级直接从无锁 → 轻量级锁 → 重量级锁。
>
> **关闭指针压缩的影响**：`-XX:-UseCompressedOops`，对象头从 12 字节变为 16 字节（Klass Pointer 从 4 变 8），堆中所有引用也从 4 字节变 8 字节，**整体内存占用增加约 40%**。所以 64 位 JVM 默认开启压缩，除非堆 > 32GB。

## 第 5 题：对象内存大小计算

### 题目

**以下代码创建的 `Student` 对象，其内存大小是多少字节？请写出计算过程。（64 位 JVM，开启指针压缩）**

```java
public class Student {
    private int age;           // 4 字节
    private boolean active;    // 1 字节
    private String name;       // 引用
    private int[] scores;      // 引用
}
```

---

### 深度回答

> **计算过程（按字段声明顺序）**：
>
> ```
> 对象头          = 12 字节（Mark Word 8 + Klass Pointer 4，开启压缩）
> int age         =  4 字节
> boolean active  =  1 字节
> String name     =  4 字节（引用，开启 UseCompressedOops）
> int[] scores    =  4 字节（引用，开启 UseCompressedOops）
> ─────────────────────────
> 原始总计         = 12 + 4 + 1 + 4 + 4 = 25 字节
> 对齐到 8 的倍数  → 32 字节（填充 7 字节）
>
> 最终大小：32 字节
> ```
>
> **注意对象头不是 16 字节**：16 字节是数组对象的对象头（12 + 4 字节数组长度），普通对象只有 12 字节。
>
> **HotSpot 的字段重排序优化**：实际上 HotSpot 会对字段按大小降序排列以减少填充浪费。优化后的布局：
>
> ```
> 对象头          = 12 字节
> int age         =  4 字节
> String name     =  4 字节
> int[] scores    =  4 字节
> boolean active  =  1 字节
> ─────────────────────────
> 原始总计         = 12 + 12 + 1 = 25 字节
> 对齐到 8 的倍数  → 32 字节（仍然填充 7 字节）
> ```
>
> 这个例子中重排序没有改善（因为 25 → 32 不变），但如果字段更多（如多个 boolean），重排序可以显著减少填充。
>
> **验证工具**：使用 **JOL（Java Object Layout）** 可以精确查看对象内存布局：
> ```java
> System.out.println(ClassLayout.parseClass(Student.class).toPrintable());
> ```
>
> **引用只占 4/8 字节，不含被引用对象大小**：不管 name 指向的 String 有多大，Student 对象本身只存 4 字节的地址。被引用的对象在堆中独立分配内存。

## 第 6 题：字符串常量池与 == 比较

### 题目

**请解释以下代码的输出结果，并说明原因：**

```java
String a = "hello";
String b = "hello";
String c = new String("hello");
String d = new String("hello");

System.out.println(a == b);          // ?
System.out.println(a == c);          // ?
System.out.println(c == d);          // ?
System.out.println(c.intern() == a); // ?
```

---

### 深度回答

> **结果**：`true`、`false`、`false`、`true`
>
> **逐行分析**：
> - `a = "hello"`：JVM 检查字符串常量池，无 "hello" → 创建 String 对象放入池中，a 指向池中对象
> - `b = "hello"`：池中有 "hello" → 直接返回池中引用，`b == a` 为 **true**
> - `c = new String("hello")`：`new` 在**堆上新建一个独立的 String 对象**（虽然 "hello" 字面量仍在池中，但 c 指向的是新对象），`a == c` 为 **false**
> - `d = new String("hello")`：同上，又一次 `new`，又一个独立对象，`c == d` 为 **false**
> - `c.intern() == a`：池中已有 "hello"（就是 a 指向的），`intern()` 直接返回池中引用，等于 a，为 **true**
>
> **`intern()` 的精确行为（JDK 1.7+）**：
> - 池中**已有**相同字符串 → 直接返回池中已有引用（不放入任何东西）
> - 池中**没有** → 把调用者的引用**直接存入池中**（不复制对象，只存引用）
>
> 所以 `c.intern()` 并没有"把 c 放进去"，因为 "hello" 已经在池中了。
>
> **对比 JDK 1.6**：1.6 中 `intern()` 会把对象**复制一份**到永久代的字符串池中，性能更差。1.7+ 改为直接存引用后效率大幅提升。
>
> **实战应用**：`intern()` 在大规模数据处理中用于字符串去重省内存——当维度值有限（如城市名只有 300 个）但事件量巨大时，调用 `intern()` 可以将内存从 O(事件量) 压缩到 O(维度数)，节省 99%+ 内存。但要注意常量池底层是 HashTable，有锁竞争，高并发场景推荐用 **Guava `Interner`** 替代。

## 第 7 题：字符串常量池与运行时常量池

### 题目

**请解释 JDK 1.8 中字符串常量池为什么从永久代移到了堆中？运行时常量池和字符串常量池有什么区别？它们分别存在哪里？**

---

### 深度回答

> **为什么从永久代替移到堆中？三个根本原因**：
>
> 1. **永久代大小固定**：通过 `-XX:MaxPermSize` 设定后启动期间不可变，设小了报 `OOM: PermGen space`，设大了浪费内存，运维很难调优
> 2. **GC 回收率极低**：永久代的 GC 触发条件苛刻（必须 Full GC），字符串池中的无用字符串长期得不到回收，造成内存泄漏假象
> 3. **永久代整体被废弃**：JDK 1.8 用**元空间（Metaspace）**替代永久代，元空间使用操作系统本地内存，只存类元信息；字符串对象不适合放在本地内存中，自然留在堆里
>
> **两个池的本质区别**：
>
> | | 运行时常量池 | 字符串常量池 |
> |--|-------------|-------------|
> | **位置** | 元空间（本地内存） | 堆（JVM 内存） |
> | **存的内容** | Utf8 **原始字节** + 符号引用索引 | 真正的 `java.lang.String` **对象** |
> | **数量** | 每个 Class 一份 | 全局唯一 |
> | **生命周期** | 随类的卸载而回收 | 随 GC 回收 |
> | **动态性** | 运行期可扩展 | 通过 `intern()` 添加 |
>
> **类比理解**：运行时常量池是"快递单"（记录字符串内容和索引关系），字符串常量池是"仓库"（存放真正的 String 对象）。`ldc` 指令执行时，JVM 根据运行时常量池中的 Utf8 字节去堆的字符串常量池中查找或创建对应的 String 对象。
>
> **实战影响**：如果应用中动态加载大量类（如 OSGi、热部署场景），运行时常量池会膨胀，可能导致 `OOM: Metaspace`。可以通过 `-XX:MaxMetaspaceSize` 限制，同时监控类加载数量（`-XX:+TraceClassLoading`）。字符串常量池的膨胀则导致 `OOM: Java heap space`，两者的排查和调优方向完全不同。

## 第 8 题：static final 与 static 的 JVM 处理方式

### 题目

**以下代码，`static final` 和 `static` 声明的字符串，在 JVM 中的处理方式有何不同？请从字节码和内存两个角度解释。**

```java
public class Demo {
    public static final String TYPE = "ADMIN";   // ①
    public static String NAME = "ADMIN";         // ②

    public void test() {
        System.out.println(TYPE);
        System.out.println(NAME);
    }
}
```

---

### 深度回答

> **核心区别：编译期内联 vs 运行期字段访问**
>
> **字节码角度**：
>
> ```
> // 使用 TYPE 的地方（编译期内联）：
> ldc  #4    // String "ADMIN"  ← 直接加载字面量，根本不访问 TYPE 字段
>
> // 使用 NAME 的地方（必须从字段读取）：
> getstatic  Demo.NAME          ← 去堆中 Class 对象里读 NAME 字段值
> ```
>
> **内存角度**：
> - `"ADMIN"` 这个 String 对象 → **始终在堆的字符串常量池中**（不管是 `final` 还是非 `final`，字符串对象只在池中有一份）
> - TYPE 字段 → 存在于堆中 Class 对象里，但**运行时基本不被访问**（已被编译器内联替换）
> - NAME 字段 → 存在于堆中 Class 对象里，**每次使用都要通过 `getstatic` 读取**
>
> **`static final` 成为编译期常量必须同时满足三个条件**：
> 1. `final` 修饰
> 2. 类型是基本类型或 `String`
> 3. 用**编译期可确定的常量表达式**初始化
>
> **反例**：`static final Person p = new Person()` **不是**编译期常量，因为 `new` 是运行期操作，不能内联，字段存在堆中 Class 对象里，每次访问走 `getstatic`。同理 `static final String s = new String("hello")` 也不是编译期常量。
>
> **性能影响**：内联后 `ldc` 指令直接从常量池加载，比 `getstatic`（需要先找到 Class 对象，再读字段）**快一个数量级**。所以高频访问的配置值推荐用 `static final`。
>
> **实战坑点**：如果一个 `static final` 常量定义在 A 类中，B 类使用了它，编译后 B 类的字节码中已经内联了该值。如果只重新编译 A 类而不编译 B 类，**B 类中仍然是旧值**——这在增量编译时容易踩坑。解决方案：修改常量后**全量重新编译**。

## 第 9 题：intern() 在 JDK 1.7+ 的行为

### 题目

**以下代码，`s1 == s2`、`s1 == s3`、`s2 == s3` 的结果分别是什么？请解释 JDK 1.7+ 下 `intern()` 的行为。**

```java
String s1 = new String("a") + new String("b");
String s2 = s1.intern();
String s3 = "ab";
```

---

### 深度回答

> **结果**：`s1 == s2` → **true**，`s1 == s3` → **true**，`s2 == s3` → **true**
>
> **逐行分析**：
>
> ```java
> String s1 = new String("a") + new String("b");
> // 运行期拼接，s1 = "ab"，在堆上新建的对象
> // 关键："ab" 此时不在字符串常量池中（不是编译期字面量）
>
> String s2 = s1.intern();
> // 检查常量池：没有 "ab"
> // JDK 1.7+：把 s1 指向的对象的引用直接存入常量池（不复制对象！）
> // s2 = s1（同一个引用）→ true
>
> String s3 = "ab";
> // 检查常量池：已有 "ab"（就是 s1 的引用，刚才 intern 放进去的）
> // s3 = s1（同一个引用）→ true
> // s2 也等于 s1 → s2 == s3 → true
> ```
>
> **JDK 版本差异（这是高频考点）**：
>
> | JDK 版本 | 池中不存在时的行为 | s1 == s2 |
> |---------|------------------|----------|
> | JDK 1.6 | 把对象**复制一份**到永久代字符串池 | **false** |
> | **JDK 1.7+** | **直接存储堆中对象的引用**（不复制） | **true** |
>
> JDK 1.6 中 `s1 == s2` 是 `false`，因为 `intern()` 复制了一份到永久代，返回的是副本引用。JDK 1.7+ 改为直接存引用后，池中存的就是 s1 本身，所以 `s1 == s2` 为 `true`。
>
> **对比变体**：如果代码改为先声明字面量再 intern：
> ```java
> String s3 = "ab";                // 先把 "ab" 放入池中
> String s1 = new String("a") + new String("b");
> String s2 = s1.intern();         // 池中已有，返回 s3 的引用
> System.out.println(s1 == s2);    // false（s2 指向 s3，不是 s1）
> System.out.println(s2 == s3);    // true
> ```
> 这个变体中 `s1 == s2` 是 `false`，因为池中已有 "ab"，`intern()` 返回的是池中已有的引用（s3），而不是 s1。
>
> **实战应用**：`intern()` 在大数据场景下用于字符串去重，但要注意底层 StringTable 是固定大小的 HashTable（默认 60013 桶），大量 intern 可能造成哈希冲突降低性能。生产环境推荐用 **Guava `Interner`**（可配置弱引用和并发度）。

## 第 10 题：JDK 1.8 JVM 完整内存结构

### 题目

**请描述 JDK 1.8 JVM 完整的运行时内存结构，标注每个区域存储的内容、线程属性（私有/共享），以及对应的 OOM 异常类型。**

---

### 深度回答

> ```
> JVM 运行时数据区（JDK 1.8 / HotSpot）
>
> ═══ 线程私有（每个线程独立一份）═══
>
> ├── 程序计数器（PC Register）
> │   存储：当前线程执行到的字节码行号
> │   异常：无（唯一不会 OOM 的区域）
> │   说明：线程切换时靠它恢复执行位置；执行 Native 方法时为 undefined
> │
> ├── 虚拟机栈（VM Stack）
> │   存储：每个方法调用对应一个栈帧
> │     栈帧包含：局部变量表、操作数栈、动态链接、方法返回地址
> │   异常：StackOverflowError（递归过深）/ OutOfMemoryError（无法申请足够栈空间）
> │   参数：-Xss 调整栈大小（默认一般 512KB~1MB）
> │
> └── 本地方法栈（Native Method Stack）
>     存储：Native 方法（C/C++）的调用信息
>     异常：StackOverflowError / OutOfMemoryError
>     说明：HotSpot 中与虚拟机栈合并实现
>
> ═══ 线程共享（所有线程共同使用）═══
>
> ├── 堆（Heap）  ← 内存最大的一块，GC 管理的主要区域
> │   存储：对象实例、数组、字符串常量池（String Table）、静态变量
> │   结构：新生代（Eden 80% + Survivor0 10% + Survivor1 10%）+ 老年代
> │   异常：OutOfMemoryError: Java heap space
> │   参数：-Xms（初始堆大小）、-Xmx（最大堆大小）
> │   对象生命周期：new → Eden → Minor GC 存活 → Survivor（年龄+1）→ 老年代
> │
> └── 元空间（Metaspace）  ← 使用操作系统本地内存，不在 JVM 堆中
>     存储：类元信息（类名、父类、接口、字段、方法字节码）
>           运行时常量池（每个 Class 一份，含字面量字节和符号引用）
>           JIT 编译后的本地代码
>     异常：OutOfMemoryError: Metaspace
>     参数：-XX:MetaspaceSize（初始大小）、-XX:MaxMetaspaceSize（最大限制）
>     特点：默认无上限，按需扩展；类卸载时对应元信息被回收
> ```
>
> **与 JDK 1.6/1.7 对比**：
>
> | 区域 | JDK 1.6 | JDK 1.7 | JDK 1.8 |
> |------|---------|---------|---------|
> | 字符串常量池 | 永久代 | **堆** | **堆** |
> | 静态变量 | 永久代 | **堆** | **堆** |
> | 类元信息 | 永久代 | 永久代 | **元空间** |
> | 运行时常量池 | 永久代 | 永久代 | **元空间** |
>
> **实战调优经验**：
> - 堆 OOM → 检查是否有内存泄漏（大集合不释放、静态 Map 无限增长），用 MAT 分析 heap dump
> - 元空间 OOM → 检查是否动态加载了过多类（CGLIB 动态代理、热部署），用 `-XX:+TraceClassLoading` 监控
> - 栈溢出 → 检查递归深度，或用 `-Xss` 适当增大栈大小
>
> **一句话总结**：JDK 1.8 的 JVM 内存设计哲学是——**对象和字符串放堆里由 GC 管理，类元信息放元空间用本地内存管理**，各司其职，解决了永久代时代大小固定、GC 低效的痛点。
